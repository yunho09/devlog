## 요약
냉장고 공유 기능 구현을 위해 초대 코드 발급·조회, 코드로 참여, 멤버 목록 조회 및 멤버 내보내기/나가기 API를 추가했습니다.
소유자(OWNER)와 멤버(MEMBER)의 권한을 구분해 접근을 제어하며, 비멤버 접근 시 냉장고 존재 여부를 숨기기 위한 404 예외 처리를 적용했습니다.
동시 요청에 의한 중복 생성 및 참여를 방지하기 위해 비관적 잠금과 데이터베이스 unique 제약 조건을 활용했습니다.

## 변경 내용
- **초대 코드 생성 및 조회 API 추가**: 소유자(OWNER) 전용 초대 코드 발급/갱신(`POST /api/fridges/{fridgeId}/invites`) 및 활성 코드 조회(`GET /api/fridges/{fridgeId}/invites/active`) 구현 (8자리 영숫자 조합, 24시간 유효, 새 코드 발급 시 이전 코드 비활성화).
- **냉장고 참여 및 멤버 관리 API 추가**: 코드를 이용한 참여(`POST /api/fridges/join`), 멤버 목록 조회 (`GET /api/fridges/{fridgeId}/members`), 멤버 강퇴(`DELETE /api/fridges/{fridgeId}/members/{userId}`), 스스로 나가기(`DELETE /api/fridges/{fridgeId}/members/me`) 추가.
- **동시성 및 권한 제어**:
  - 초대 코드 생성 시 냉장고 행에 비관적 잠금(`PESSIMISTIC_WRITE`) 적용.
  - 동시에 가입 요청 시 `(fridge_id, user_id)` unique 제약 조건을 통해 중복 참여 시 409(`ALREADY_FRIDGE_MEMBER`) 반환.
  - 멤버를 내보낼 경우 기존 초대 코드도 함께 무효화되도록 로직 추가.
  - 비멤버가 접근할 경우 냉장고 존재 여부를 노출하지 않도록 `FRIDGE_NOT_FOUND`(404) 처리.

## 의도
사용자들이 초대 코드를 통해 하나의 냉장고를 함께 관리할 수 있도록 공유 기능을 제공하기 위한 목적입니다. 동시 요청 상황에서도 초대 코드와 멤버 상태의 정합성을 유지하고 보안 요건(권한별 접근 제어 및 비멤버에 대한 정보 은닉)을 충족하기 위해 변경을 진행했습니다.

## 트러블 슈팅
- MySQL REPEATABLE READ 격리 수준에서 트랜잭션 내 일반 조회가 첫 조회 시점의 스냅샷을 읽어, 동시 요청 또는 앞선 요청이 생성한 최신 초대 코드를 비활성화할 때 놓치는 문제 발생 → `findAllActiveByFridgeIdForUpdate` 메서드를 통해 비관적 잠금(`FOR UPDATE`) 조회를 수행함으로써 항상 최신 상태의 초대 코드를 읽어와 무효화 처리하도록 해결.

## 생각 정리

2. 멤버 내보내기 시 해당 냉장고의 활성 초대 코드를 함께 무효화하는 정책이 다른 대기 사용자나 사용자 경험(UX) 관점에서 적절한 방식인가?
3. 동시성 제어 및 트랜잭션 격리 수준으로 인해 발생하는 버그를 직접 잠금 조회를 통해 해결하면서 데이터베이스 정합성에 대해 어떤 점을 느꼈는가?
