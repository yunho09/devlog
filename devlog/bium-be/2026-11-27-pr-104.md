## 요약
본 PR은 냉장고 재료 조작 및 도감 사진 변경 시 권한 확인보다 비관적 잠금(Lock)이나 파일 검증이 먼저 실행되던 순서 문제를 해결합니다. 냉장고 멤버 권한 검사를 잠금보다 앞서 수행하도록 변경하여, 권한이 없는 사용자가 타인의 잠금을 대기하지 않고 즉시 404 응답을 받도록 개선했습니다. 또한 도감 사진 변경 시에도 재료 권한 확인 및 잠금을 파일 디코딩/검사보다 먼저 진행하도록 로직 순서를 정비했습니다.

## 변경 내용
- `FridgeItemService`의 `create`, `createAll`, `deleteAll` 메서드에서 `validateMember`를 `lockFridge`보다 먼저 호출하도록 순서 변경.
- `changePosition` 메서드가 멤버 확인 후 냉장고 및 재료를 잠그는 `lockAccessibleItem`을 사용하도록 수정.
- 잠금 전 멤버 확인 조회가 스냅샷을 취함에 따라 발생하던 순번 계산 문제를 해결하기 위해, 미사용 `findMaxSortOrder`를 제거하고 `findAllInSectionForUpdate`로 최신 상태의 재료를 잠그며 순번을 산출하도록 변경.
- `IngredientCatalogService.changeImage`에서 파일 검증(`toPng`) 전에 권한 확인 및 잠금(`lockUsableCatalog`)을 먼저 수행하도록 수정.
- 권한 없는 사용자의 요청이 잠금을 기다리지 않고 즉시 404로 거부되는지 확인하는 `FridgeItemWriteLockOrderTest` 및 컨트롤러 검증 테스트 추가.

## 의도
권한이 없는 유저의 요청이 타인의 냉장고 잠금을 대기하면서 불필요한 트랜잭션 대기 시간과 동시성 병목을 유발하는 현상을 막기 위함입니다. 또한 파일 검증 및 디코딩과 같은 비중 있는 작업 이전에 권한 검사를 완료하여 무단 접근 차단과 자원 효율성을 도모하고자 했습니다.

## 트러블 슈팅
- `validateMember`를 잠금 앞으로 이동하면서 MySQL REPEATABLE READ 환경의 스냅샷 조회 때문에 `findMaxSortOrder`가 동시 커밋된 최신 재료를 읽지 못하는 문제 → 일반 조회 대신 `findAllInSectionForUpdate`를 통해 잠금과 동시에 최신 목록을 읽어 순번을 매기도록 해결.
- 도감 사진 변경 시 잠금 전 단순 확인 조회를 추가하면 스냅샷 이슈로 동시 요청 간 사진 덮어쓰기나 옛 사진 남음 문제가 발생하는 문제 → 잠금을 먼저 수행한 후 잠금 안에서 파일 변환(`toPng`)을 처리하여 동시성 안전성 확보.
