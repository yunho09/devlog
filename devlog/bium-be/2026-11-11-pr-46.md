# 2026-11-11

## 요약
식약처 식품영양성분 DB API를 연동하여 재료의 100g당 영양 정보를 조회하는 `GET /api/fridge-items/{itemId}/nutrition` API를 구현했습니다. 기존 도감 ID 기준의 `nutrition_info` 테이블을 재료 이름(검색어) 기준의 `food_nutrition` 테이블로 개편하여 영수증 입력 재료 지원 및 사용자 간 공통 캐싱이 가능하도록 처리했습니다. 외부 API 응답 지연에 대비해 DB 트랜잭션을 분리하고, 타임아웃 제한 및 띄어쓰기·동의어 처리 매칭 알고리즘을 적용했습니다.

## 변경 내용
- `GET /api/fridge-items/{itemId}/nutrition` 조회 API 및 응답 DTO 추가 (소수점 둘째 자리 반올림, 데이터 없을 시 null 반환)
- 공공데이터포털 식약처 식품영양성분 DB API(`FoodNtrCpntDbInfo03`) 연동 클라이언트 및 환경변수(`NUTRITION_API_KEY`) 설정 추가
- 엔티티 구조 변경: 도감 ID 기반 `NutritionInfo` 제거, 재료 이름/검색어 키 기반 `FoodNutrition` 추가
- 식품 선택 매칭 로직(`FoodMatcher`) 추가: 띄어쓰기 제거, "계란"→"달걀" 변환, 정확한 이름 매칭 및 원재료(`양파, 생것` 등) 우선순위 정렬
- 외부 API 응답 지연 방어: 조회 로직에 DB 트랜잭션 미적용, 1페이지 5초 초과 시 2페이지 조회 생략
- 캐시 관리: 검색어별 30일간 결과 저장, 30일 지난 미조회 건 재찾기 실패 시 이전 null 데이터 유지 및 502 에러 방지
- 보안 및 예외 처리: 외부 호출 실패 시 `502 NUTRITION_FETCH_FAILED` 반환, API 키 노출 방지를 위해 에러 로그 주소 단순화 및 서버 구동 시 1회만 키 확인 로그 출력

## 의도
도감 재료뿐만 아니라 영수증으로 등록한 재료의 영양 정보를 조회하고, 사용자 간 동일한 재료(예: "두부")에 대해 중복으로 외부 API를 호출하는 비용을 줄이기 위해 데이터 구조를 검색어 기반 공유 캐시 형태로 개편했습니다. 식약처 API의 불규칙한 검색 방식과 응답 지연으로부터 DB 커넥션 및 사용자 응답 시간을 보호하기 위함입니다.

## 트러블 슈팅
- 검색어 띄어쓰기 불일치 및 1페이지 내 정확한 상품 미존재 문제 → 검색어의 띄어쓰기를 일률 제거("방울 토마토" → "방울토마토")하고, 1페이지에 완전 일치 식품이 없으면 2페이지까지 조회를 확장하도록 수정했습니다.
- API 키 누락 시 매 요청마다 과도하게 에러 로그가 남는 문제 → 요청 시점이 아닌 서버 구동(시동) 시점에 1회만 에러 로그를 남기도록 수정했습니다.
- 식약처 API의 느린 응답 시간(4~6초) 및 쉼표 구분 원재료(`양파, 생것`)·동의어(`계란`) 검색 실패 문제 → 한 번에 500개 단위로 요청을 받고, "계란"을 "달걀"로 치환하며 쉼표 뒤 세부명을 분석하는 매칭 규칙을 적용했습니다.
- 2페이지까지 연쇄 조회 시 대기 시간이 지나치게 길어지는 문제 → 첫 페이지 조회가 5초 이상 걸린 경우 2페이지 조회를 포기하고 1페이지 결과 내에서 최선의 항목을 선택하도록 제한 로직을 추가했습니다.

3. 응답 속도가 보장되지 않는 외부 공공 API를 서비스 핵심 로직과 분리하고 캐싱 기법을 적용하면서 백엔드 개발자로서 무엇을 느끼고 배웠는가?
