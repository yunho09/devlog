# 2026-11-28

## 요약
냉장고 레시피 목록 조회 API와 레시피 삭제 API를 구현했습니다. 커서 기반 페이징을 적용해 최신순으로 레시피를 제공하며 재료 데이터는 배치 조회로 성능을 최적화했습니다. 연관 데이터 참조 보존을 위해 레시피 삭제에는 Soft Delete를 적용하고, 관련 서비스에서 삭제된 레시피에 대한 404 처리를 일관되게 적용했습니다.

## 변경 내용
- **레시피 목록 조회 API 추가 (`GET /api/fridges/{fridgeId}/recipes?cursor=`)**:
  - 추천(`RECOMMEND`) 및 만들고 싶은 음식(`TARGET`) 레시피를 ID 내림차순 최신순으로 12개씩 제공.
  - 레시피마다 재료를 N+1로 개별 조회하지 않고 일괄 읽기(Batch Fetch)로 처리.
  - 응답 포맷: `{ recipes: RecipeResponse[], nextCursor }` (다음 페이지가 없으면 `nextCursor`는 `null`).
- **레시피 삭제 API 추가 (`DELETE /api/recipes/{recipeId}`)**:
  - HTTP 204 응답 반환 및 냉장고 멤버 권한 검증.
  - 요리 기록 및 장보기 목록의 외래키 참조 보존을 위해 `recipes.deleted_at` 컬럼을 사용하는 Soft Delete 방식으로 동작.
- **삭제된 레시피 404 처리**:
  - `RecipeFinder`, `CookingService` 수정: 삭제된 레시피는 목록, 상세, 요리 후보, 요리 완료, 부족 재료 담기 기능에서 `RECIPE_NOT_FOUND` (404)로 처리.
- **권한 처리 연동**:
  - 비멤버 접근 시 목록 조회는 `FRIDGE_NOT_FOUND`, 삭제는 `RECIPE_NOT_FOUND` 반환.
- **검증 코드 추가**:
  - `RecipeListControllerTest` 작성 (페이징, soft delete, 삭제 후 목록/상세 제외, 요리 기록 유지, 권한/인증 예외 케이스 검증).

## 의도
사용자가 냉장고 내 레시피를 최신순으로 효율적으로 조회하고 레시피를 삭제할 수 있는 기능을 제공하기 위해 변경했습니다. 하드 삭제 시 발생할 수 있는 요리 기록 및 장보기 목록과의 참조 무결성 파괴를 방지하기 위해 소프트 삭제 방식을 채택했습니다.
