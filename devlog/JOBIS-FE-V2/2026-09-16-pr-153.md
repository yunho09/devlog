## 요약
학생용 앱 홈 화면에 새로운 배너 디자인 및 기능을 적용하였습니다. API 연동 및 프리페치까지 구현했으나 백엔드 및 디자인이 확정되지 않아 최종 시안의 문구와 이미지로 임시 하드코딩하여 롤백하였습니다. 또한 코드 리뷰 피드백을 반영하여 `div` 태그의 클릭 이벤트 대신 `Link` 컴포넌트를 사용하여 키보드 접근성을 개선했습니다.

## 변경 내용
- **임시 하드코딩 및 스타일 반영**: 최종 시안을 기반으로 그라데이션, 문구, 빌딩 이미지(`public/office-building.png`)를 수동 반영
- **이동 경로 규약 반영**: 요구사항에 맞는 배너 클릭 이동 경로 수정
- **웹 접근성 개선**: 단순 클릭 이벤트 핸들러가 달린 `div` 요소를 `Link` 컴포넌트로 변경하여 키보드로도 배너를 조작할 수 있도록 개선

## 의도
백엔드 스펙 및 디자인이 완성되기 전까지 우선적으로 UI 구조를 유지하기 위해 API 호출 대신 시안대로 하드코딩을 적용했습니다. 또한, 단순 UI 디자인 작업에 머무르지 않고 키보드 사용자와 같은 웹 접근성을 보장할 수 있도록 시맨틱한 링크 구조를 활용하려 했습니다.

## 트러블 슈팅
- **디자인 및 백엔드 미확정으로 인한 연동 보류** → 홈 배너 API를 붙이고 프리페치까지 설정했으나, 최종 확정이 미뤄짐에 따라 API 의존성을 끊고 기존 프리페치/연동 로직을 이전 상태로 되돌린 뒤 시안 문구와 이미지로 하드코딩하여 문제를 우회했습니다.
- **키보드 접근성 결여 우려** → 단순 `div` 태그에 `onClick`만 정의했을 때 키보드로 초점을 잡을 수 없는 문제가 있었으나, 코드 리뷰 피드백을 반영하여 `Link` 컴포넌트로 교체해 키보드 내비게이션이 작동하도록 개선했습니다.

## 생각 정리
1. 백엔드 명세가 바뀔 여지가 많을 때, 향후 하드코딩된 UI를 API 통신 코드로 매끄럽게 교체하려면 어떤 컴포넌트 설계 방식이 가장 효율적일까요?
2. `div` 클릭 요소를 `Link` 컴포넌트로 바꿨을 때, 스타일링이나 SEO/접근성 관점에서 추가로 점검해야 하는 요소는 무엇이 있을까요?
3. 이미 한 차례 완성했던 API 연동 코드를 스펙 미확정으로 인해 다시 하드코딩 상태로 되돌리는 과정을 거치며 어떤 점을 느꼈나요?
