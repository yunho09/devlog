## 작업 내용

### 1. 구글 OAuth 클라이언트 (`domain/auth/client`)
- `GoogleOAuthClient.fetchUserInfo(code, redirectUri)`: 두 번 호출한다
  1. `POST https://oauth2.googleapis.com/token`: 인가 코드를 액세스 토큰으로 바꾼다. 구글 토큰 API는 JSON이 아니라 **form**(`application/x-www-form-urlencoded`)으로 받아서 `code, client_id, client_secret, redirect_uri, grant_type=authorization_code`를 form으로 보낸다
  2. `GET https://openidconnect.googleapis.com/v1/userinfo` (`Authorization: Bearer ...`): `sub`, `email`, `email_verified`를 읽는다
- 구글 응답 오류는 두 가지로 나눈다

| 구글 응답 | 우리 응답 | 이유 |
| --- | --- | --- |
| 토큰 교환 4xx (`invalid_grant`: 코드 만료·재사용, `redirect_uri_mismatch`) | 401 `GOOGLE_AUTH_FAILED`, description `인가 코드 만료·재사용` | 요청이 잘못됨. 구글 로그인을 다시 하면 된다 |
| 5xx, 타임아웃, 네트워크 오류 | 502 `GOOGLE_SERVER_ERROR` | 구글 쪽 문제. 잠시 후 다시 시도하면 된다 |
| `email_verified=false` | 401, description `인증되지 않은 구글 이메일` | 인증 안 된 이메일을 믿으면 남의 이메일로 그 사람 계정에 연결을 시도할 수 있다 |
| userinfo에 `sub`·`email` 없음 (email scope 누락) | 401, description `구글 계정 정보(sub·email) 없음` | |

- 4xx일 때는 구글 응답 본문(`{"error":"invalid_grant",...}`, 비밀값 없음)을 warn 로그로 남긴다. client id/secret을 잘못 넣어도 401로 보이기 때문에 원인은 로그로 확인한다
- **`RestClient`를 직접 만든 이유**: 스프링 부트 4는 restclient 스타터가 없으면 `RestClient.Builder`를 자동으로 만들어주지 않는다. `build.gradle`을 건드리지 않고 `GoogleOAuthConfig`에서 직접 만든다
- **타임아웃 (연결 3초, 응답 5초)**: 타임아웃이 없으면 구글이 응답하지 않을 때 요청 스레드가 계속 기다리고, 그런 요청이 쌓이면 서버 전체가 멈춘다. RestClient가 기본으로 쓰는 JDK `HttpClient`에 타임아웃만 더했다
- **생성자로 `RestClient.Builder`를 받는 이유**: 테스트에서 `MockRestServiceServer`를 붙인 Builder를 넣으면 실제 구글 없이 응답을 흉내 낼 수 있다
- 구글 이메일은 이메일 가입과 같은 기준으로 `trim + 소문자`로 맞춘다 (`GoogleUserInfo` compact constructor)

### 3. 구글 로그인 `POST /api/auth/google`
`GoogleAuthService.login`은 아래 순서로 결과를 정한다.

| 순서 | 조건 | result | 응답 필드 |
| --- | --- | --- | --- |
| 1 | `google_sub`가 같은 회원이 있음 | `LOGGED_IN` | accessToken, refreshToken, onboardingStatus |
| 2 | 같은 이메일의 이메일 가입 계정이 있음 | `LINK_REQUIRED` | linkToken, email (토큰 없음) |
| 3 | 둘 다 없음 | `SIGNED_UP` | accessToken, refreshToken, onboardingStatus(`NOT_STARTED`) |

- 계정은 **sub로 먼저** 찾는다. 이메일은 바뀔 수 있지만 sub는 구글 계정마다 고정이다
- **같은 이메일이어도 자동으로 연결하지 않는다**: 비밀번호를 확인하지 않고 연결하면, 이메일만 같은 구글 계정을 가진 사람이 남의 계정에 들어갈 수 있다. 그래서 `LINK_REQUIRED` + `linkToken`을 주고 비밀번호는 연결 API에서 확인한다
- 같은 이메일 계정이 **비밀번호 없는 구글 전용 계정**(다른 sub)이면 비밀번호로 본인 확인을 할 수 없어서 409 `이미 가입된 이메일입니다.`
- `SIGNED_UP`: `User.createWithGoogle(email, sub, googleEmail)`로 비밀번호 없는 계정을 만들고 바로 토큰을 준다. 약관 동의 저장과 403 처리는 이번 PR에 없다 (확인 필요 참고)
- **메서드 전체를 `@Transactional`로 묶지 않은 이유**: 묶으면 구글 응답을 기다리는 몇 초 동안 DB 커넥션을 붙잡고 있다. 구글이 느려지면 커넥션 풀이 바닥나서 다른 API까지 멈춘다. 그래서 구글 호출을 먼저 끝내고, DB 작업은 `UserService`·`TokenService`가 각자 트랜잭션으로 처리한다 (가입 직후 토큰 발급만 실패하면 계정은 남는다. 다시 구글 로그인하면 `LOGGED_IN`으로 들어온다)
- 응답은 `GoogleLoginResponse` record 하나다. `@JsonInclude(NON_NULL)`이라 `LINK_REQUIRED`에는 토큰 필드가 아예 없다. `loggedIn / signedUp / linkRequired` 정적 메서드로만 만들어서 result와 필드 조합이 어긋날 수 없다
- 로그인 시도 제한(IP·계정)은 적용하지 않는다 (FUNC-001-02, FUNC-001-03)

### 4. 연결 대기 정보 Redis `auth:link:{linkToken}` (`GoogleLinkTokenService`)
- 값은 JSON 문자열 `{"memberId", "googleSub", "googleEmail"}`, TTL 10분, linkToken은 랜덤 UUID
- **sub를 응답에 내려주지 않는 이유**: 클라이언트가 sub를 들고 있다가 연결 요청에 다시 보내면, 클라이언트가 sub를 바꿔 끼울 수 있다. sub는 서버(Redis)에만 두고 클라이언트에는 그걸 가리키는 추측할 수 없는 linkToken만 준다
- JSON 변환은 부트가 자동으로 만드는 Jackson 3 `JsonMapper` 빈을 쓴다

### 5. 로그인 중 구글 계정 연결 `POST /api/auth/google/link`
한 `@Transactional` 메서드에서 아래 순서로 처리한다.
1. linkToken으로 Redis에서 연결 정보를 읽는다. 없으면 (10분 만료 또는 없는 값) 401, description `linkToken 만료`
2. 연결할 회원을 찾는다. 대기 중에 탈퇴해서 없으면 같은 401
3. `login:fail:{email}` 잠금 확인. 잠겨 있으면 비밀번호를 보지 않고 423
4. 비밀번호가 틀리면 실패 횟수 +1 후 401 `비밀번호가 올바르지 않습니다.` **이메일 로그인과 같은 키에 합산**하므로 5번째 실패는 423이다. 다시 시도할 수 있도록 linkToken은 지우지 않는다
   - 시도는 비밀번호를 비교하기 **전에** `LoginAttemptService.start()`로 먼저 기록한다 (#2 리뷰 반영: 동시에 여러 번 보내도 5번까지만 비교). 비밀번호가 맞으면 바로 `reset()`해서, 아래 409로 끝나도 맞은 비밀번호가 실패로 남지 않는다
5. 이 구글 계정이 그 사이 다른 회원에게 연결됐거나, 이 회원에게 다른 구글 계정이 연결됐으면 409 `다른 계정에 이미 연결된 구글 계정입니다.`
6. `UserService.linkGoogle`로 sub·구글 이메일 저장. 저장 직후 **flush**해서, 5번 확인과 저장 사이에 다른 요청이 같은 sub를 먼저 연결한 경우(`google_sub` UNIQUE 위반)를 커밋 시점이 아니라 그 자리에서 잡아 409로 바꾼다
7. linkToken 삭제 → 토큰 발급

### 구글 콘솔 설정
- Google Cloud Console > API 및 서비스 > 사용자 인증 정보 > **OAuth 클라이언트 ID**, 유형은 **웹 애플리케이션**
- **승인된 리디렉션 URI**는 FE가 보내는 `redirectUri`와 **정확히 같아야 한다** (스킴·포트·끝의 `/`까지). 하나라도 다르면 구글이 `redirect_uri_mismatch`(400)를 줘서 401이 된다. 로컬·운영 주소를 각각 등록한다
- 동의 화면 scope는 **`openid email profile`** (캘린더 권한은 여기서 받지 않는다). email scope가 빠지면 이메일이 오지 않아 401이 된다
- 발급된 값을 `.env`의 `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`에 넣는다

## 확인 필요
- **SIGNED_UP 약관 동의**: 명세는 "필수 약관 동의 전까지 다른 API가 403"이지만, 403의 message·허용 API 목록이 정의되지 않았고 동의 설정 변경 API(`PATCH /api/members/me/consents`)도 아직 없다. 이슈대로 P1에서 결정한다. 지금은 SIGNED_UP 계정이 동의 없이 다른 API를 쓸 수 있다
- **`email_verified=false`의 응답**: 명세에 status·message가 없어서 401 `GOOGLE_AUTH_FAILED`(description `인증되지 않은 구글 이메일`)로 정했다
- **같은 이메일 계정에 이미 다른 구글 계정이 연결된 경우** (명세에 없음): `LINK_REQUIRED`로 연결하면 기존 구글 연결이 말없이 덮어써진다. 그래서 구글 전용 계정과 같은 409 `이미 가입된 이메일입니다.`로 막았다. 바꾸려면 마이페이지에서 연결 해제 후 다시 연결하는 흐름이 맞아 보인다
- **연결 API의 409**: 기능 명세(FUNC-001-04)에는 있고 API 페이지에는 없다. `GOOGLE_ACCOUNT_ALREADY_LINKED`(409)로 응답한다. "이 회원에게 그 사이 다른 구글 계정이 연결된 경우"도 같은 409라서 message가 정확히 맞지는 않는다
- **연결 성공 시 `login:fail` 삭제**: API 페이지에 없지만 로그인 API와 똑같이 지운다
- **구글 응답 4xx 구분**: client id/secret 설정 오류(`invalid_client`)도 401 `인가 코드 만료·재사용`으로 보인다. 원인은 warn 로그로 확인한다
- **동시 가입** (CodeRabbit 리뷰 반영): 조회와 가입 저장 사이에 같은 구글 계정(버튼 두 번 클릭 등)이나 같은 이메일 회원이 먼저 저장되면 UNIQUE 위반이 난다. 이때 500을 주지 않고 다시 조회해서 1)·2)와 같게 처리한다 (같은 구글 계정 → `LOGGED_IN`, 같은 이메일 → `LINK_REQUIRED` 또는 409). 다시 조회해도 없으면 원인을 모르는 위반이라 그대로 500이다
- **`state` 파라미터**: 요청에 없어서 FE가 검증하는 것으로 본다 (FUNC-001-02 "state가 일치하지 않으면 거부")
- 명세 설계 메모의 대안 (link API를 빼고 `LINK_REQUIRED`를 409로 바꾸기)은 적용하지 않았다
