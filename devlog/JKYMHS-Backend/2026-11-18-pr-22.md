### 1. 엔티티 (`domain/user/entity`)
- `User`에 컬럼 두 개를 더했다. `nickname VARCHAR(30) NULL`은 마이페이지의 이름이다. 비어 있으면 `displayName()`이 이메일 `@` 앞부분을 돌려줘서, FE가 대신 보여줄 값을 따로 만들 필요가 없다. `last_companion_type VARCHAR(20) NULL`은 AI 추천(D5)이 마지막으로 고른 동행을 저장하는 곳이다.
- `User`에 의도가 드러나는 메서드를 추가했다: `changeNickname`, `completeOnboarding`, `skipOnboarding`, `unlinkGoogle`, `changePassword`, `setInitialPassword`, `rememberCompanion`. `@Setter`는 쓰지 않는다. `skipOnboarding`은 상태가 DONE이면 엔티티 안에서 409 `ONBOARDING_ALREADY_DONE`을 던진다. "DONE이면 건너뛸 수 없다"는 규칙은 상태 전이 규칙이라 엔티티에 두었다.
- `ConsentType`에 `LOCATION(false)`를 추가해서 순서가 AGE_14, TERMS, PRIVACY, LOCATION, BEHAVIOR_DATA, EMAIL_NOTIFICATION이 됐다. 가입 API는 `ConsentType.values()`를 돌며 저장하므로, 가입하면 LOCATION이 미동의로 함께 저장된다 (가입 화면은 위치 동의를 받지 않는다).
- `UserConsent.change(agreed, now)`: 이미 동의한 항목에 다시 동의해도 `agreedAt`은 바뀌지 않는다. 같은 값을 보낼 때마다 "언제 동의했는지"가 바뀌면 기록으로 쓸 수 없기 때문이다.
- 새 enum은 `TravelStyle`(7개, `code`/`label`/`description`, 문구는 FE `mocks/data/member.ts`와 같다), `Pace`(relaxed/packed), `TimeOfDay`(early 09:00 / morning 10:00 / afternoon 13:00, `startTime()`)다. 모두 `CodeEnum`이라 JSON에는 소문자 코드로 나가고, DB에는 대문자 `name()`이 저장된다.
- 새 테이블:
  - `user_preferences`(`UserPreference`): 회원당 한 행이고 `uk_user_preferences_user_id`가 이를 DB에서 보장한다. 온보딩을 건너뛴 회원은 행이 없다. 기본값은 저장하지 않고 쓸 때 채운다. 저장해 두면 사용자가 직접 고른 값과 기본값을 구분할 수 없다.
  - `user_travel_styles`(`UserTravelStyle`): 회원당 1~3행이고 `uk_user_travel_styles_user_id_style_code`가 걸려 있다.
  - **`accessible` 컬럼 이름은 `accessible_only`로 바꿨다.** `ACCESSIBLE`이 MySQL 예약어라서 그대로 두면 `CREATE TABLE`이 문법 오류로 실패하고, 테이블이 아예 만들어지지 않는다 (테스트에서 확인했다). JSON 필드 이름은 `accessible` 그대로다.

### 2. 리포지토리
- `UserRepository.findByIdForUpdate`는 `PESSIMISTIC_WRITE`(`SELECT … FOR UPDATE`)다. 같은 회원의 요청이 동시에 와도 "확인 → 변경"이 겹치지 않게 한다. 예를 들어 취향 저장이 동시에 두 번 오면, 잠금이 없을 때는 둘 다 "행 없음"을 보고 INSERT해서 UNIQUE 위반 500이 난다.
- 지우기는 JPQL `delete` 한 번으로 한다 (`deleteAllByUserId`, 동의·취향·스타일·리프레시 토큰). 모두 `@Modifying(clearAutomatically = true, flushAutomatically = true)`다.
  - `flushAutomatically`가 필요한 이유: 이 DELETE는 1차 캐시를 비운다(clear). 비우기 전에 같은 트랜잭션에서 바꾼 엔티티(예: 새 비밀번호 해시)를 DB에 먼저 쓰지 않으면 그 변경이 조용히 사라진다.
  - 스타일을 다시 저장할 때 "엔티티 delete() 후 save()"로 하지 않은 이유: Hibernate는 flush할 때 INSERT를 DELETE보다 먼저 실행한다. 그래서 같은 스타일을 다시 고르면 (user_id, style_code) UNIQUE에 걸린다. JPQL DELETE는 그 자리에서 바로 실행된다.
- `RefreshTokenRepository.deleteAllByUserId`와 `TokenService.revokeAll(userId)`: 회원의 리프레시 토큰을 모두 **지운다**. 탈퇴할 때는 `users`를 지우기 전에 FK가 걸린 토큰 행을 먼저 없애야 한다. 비밀번호를 바꾼 뒤에는 옛 토큰이 다시 와도 "없는 토큰이라 401"이면 충분해서 폐기 기록을 남길 필요가 없다.

### 3. 서비스 (`domain/user/service`)
- `PreferenceService`
  - `save`: 회원 행을 잠근 뒤 스타일 삭제 → 취향 upsert → 스타일 insert → `completeOnboarding()` 순서로 처리한다. 스타일 DELETE가 1차 캐시를 비우기 때문에, 회원은 그 뒤에 다시 읽어서 쓴다. 잠금은 트랜잭션이 끝날 때까지 유지된다.
  - `get`: NOT_STARTED·SKIPPED이면 상태 외의 필드는 모두 null이다.
  - `skipOnboarding`: NOT_STARTED 또는 SKIPPED면 SKIPPED가 되고, DONE이면 409다.
  - `getEffective(userId)` → `EffectivePreference(styles, pace, timeOfDay, accessible, pet, status)`: 다른 도메인(D5)이 쓰는 계약이다. 온보딩을 끝내지 않은 회원은 `styles` 빈 집합(= 모든 스타일), RELAXED, MORNING, false, false다 (§5 Q19).
- `UserConsentService`
  - `getConsents`: 6개 항목을 enum 순서대로 돌려준다. 행이 없는 항목은 미동의다. 구글로 가입한 회원은 가입 API가 동의를 받지 않아서 행이 없다.
  - `updateConsents`: 필수 항목을 끄는 요청이 하나라도 있으면 **아무것도 바꾸지 않고** 400 `REQUIRED_CONSENT_CANNOT_REVOKE`다. 일부만 반영되면 FE 토글 상태와 서버 상태가 어긋나기 때문이다. 필수 항목을 켜는 요청은 받아서 저장한다(행이 없으면 만든다). 구글 가입 직후 FE가 필수 3개를 true로 보내 저장하는 흐름 때문이다. 응답에는 바꾼 항목만 enum 순서로 담는다.
  - 행동 데이터를 false로 보내면 같은 트랜잭션 안에서 `BehaviorConsentRevokedEvent`를 발행한다. D3의 동기 리스너가 행동 기록을 지우고, 리스너가 실패하면 동의 변경까지 롤백되어 500이 나간다. 이미 꺼져 있던 경우에도 다시 발행한다. 지우는 작업은 여러 번 해도 결과가 같다.
  - `isAgreed(userId, type)`: 다른 도메인용 계약이다.
  - `saveInitialConsents`는 `LocalDateTime.now()` 대신 `LocalDateTime.now(clock)`을 쓰도록 바꿨다 (G2).
- `UserService` 추가 메서드:
  - `getByIdForUpdate`: D5의 추천 횟수 확인에서도 쓴다.
  - `rememberCompanion` / `getLastCompanion`
  - `linkGoogle(Long userId, …)`: 잠근 뒤 다시 확인하고, `saveAndFlush`로 UNIQUE 위반을 그 자리에서 알 수 있게 한다.
  - `delete`
- `MemberService`: 내 정보·이름, 구글 연결/해제, 비밀번호 변경/설정, 탈퇴를 맡는다.
  - **클래스 전체에 `@Transactional`을 걸지 않았다.** 구글 연결과 구글 전용 회원의 탈퇴는 구글 서버를 부른다. 그동안 트랜잭션(DB 커넥션·회원 행 잠금)을 잡고 있으면 구글이 느려질 때 커넥션 풀이 바닥난다. `GoogleAuthService`와 같은 방식이다. 그래서 탈퇴는 구글 재인증을 트랜잭션 밖에서 먼저 끝내고, DB 작업만 `TransactionTemplate`로 한 트랜잭션에 묶는다. 같은 클래스 안의 `@Transactional` 메서드를 직접 부르면 프록시를 거치지 않아 트랜잭션이 걸리지 않기 때문에 `TransactionTemplate`을 썼다.
  - 구글 연결: 이미 구글이 연결된 회원(같은 구글 계정 포함)이면 **구글을 부르기 전에** 409를 준다. 인가 코드는 한 번만 쓸 수 있다. 그 구글 계정이 다른 회원에게 연결돼 있으면 409다. 확인과 저장 사이에 경쟁이 생기면 `DataIntegrityViolationException`이 나는데, 이것도 409로 바꾼다.
  - 비밀번호 변경: 확인 순서는 구글 전용 409 → 현재 비밀번호 불일치 401 → 새 비밀번호가 현재와 같으면 400이다. 통과하면 해시를 바꾸고 `revokeAll` 후 `TokenService.issue(user, User-Agent)`로 이 기기에 새 토큰 쌍을 발급한다.
  - 탈퇴는 한 트랜잭션 안에서 다음 순서로 진행한다.
    1. 회원 행 잠금
    2. (비밀번호 회원) 비밀번호 확인
    3. `UserWithdrawnEvent` 발행 (D3~D6 동기 리스너가 자기 행 삭제)
    4. 토큰·동의·취향·스타일 삭제
    5. 회원 삭제

    이벤트를 회원 삭제보다 먼저 발행해야 FK 위반이 나지 않는다. 본인 확인 규칙은 이렇다. 비밀번호가 있는 회원은 비밀번호로 확인한다(구글도 연결돼 있어도 같다). 구글로만 가입한 회원은 인가 코드로 받은 `sub`가 연결된 구글 계정과 같아야 한다. 본문이 없거나 필요한 값이 빠지면 401 `IDENTITY_VERIFICATION_FAILED`다.
- `WithdrawSummaryContributor` 인터페이스와 `WithdrawSummaryService`: 회원 도메인이 여행·찜·캘린더 Repository를 몰라도 되게, 숫자는 각 도메인이 `contribute(userId, counts)`로 채운다. 키는 `tripCount`·`planCount`(D4), `wishCount`(D3), `calendarEventCount`(D6)다. 구현 빈이 없으면 스프링이 빈 리스트를 넣어서 모두 0이 나간다.

### 4. API (`MemberController`, `TravelStyleController`)
- 모든 요청 본문은 `@Valid` record로 받고, 필드 검증 메시지는 한국어다. Boolean 값은 래퍼 타입을 써서 값이 빠졌을 때 false로 짐작하지 않고 400을 준다.
- 비밀번호 규칙(영문+숫자 8~20자, 키보드 기본 문자만)은 `PasswordRule` 상수로 두었다. 애너테이션 속성에는 컴파일 시점 상수만 넣을 수 있어서 `static final String`이다. 가입 API(`SignupRequest`)와 같은 정규식이다.
  - **추가 수정 (`92587cd`)**: 원래 `\S{8,20}`이라 한글·이모지도 통과했다. 이모지는 1글자 4바이트라 `"a1"+이모지 18개`(20자, 74바이트)는 규칙을 통과하지만, BCrypt가 72바이트 넘는 비밀번호를 저장하지 못해 가입이 500이었다. 그래서 `[\x21-\x7E]{8,20}`(ASCII 33~126: 영문·숫자·특수문자)로 바꿨다. `SignupRequest`도 같이 바꿨다. 한글·이모지가 든 비밀번호는 이제 400이다(메시지는 그대로). 테스트: 가입 규칙 위반에 한글·이모지 2개 추가, 특수문자 비밀번호 가입 성공 1개 추가, 비밀번호 변경 규칙 위반에 한글 추가
- `SecurityConfig`: `GET /api/regions`, `/api/categories`, `/api/travel-styles`를 `permitAll`로 열었다. 조회(GET)만 열었고, 같은 경로라도 POST는 401이다 (테스트로 확인).

## 직접 확인할 것
- 새 환경변수는 없다. 구글 연결과 구글 회원 탈퇴를 실제로 해보려면 기존 `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`가 필요하다.
- 로컬 DB가 `ddl-auto: update`로 이미 만들어져 있으면 `users.nickname`, `users.last_companion_type` 컬럼과 `user_preferences`, `user_travel_styles` 테이블이 자동으로 추가된다. 그런데 `user_consents.consent_type`이 예전에 Hibernate가 만든 CHECK 제약(`consent_type in (...)`)을 갖고 있으면, `update`가 그 제약을 고치지 않아서 LOCATION을 저장할 때 실패할 수 있다. 그때는 그 테이블의 CHECK 제약을 지우거나 로컬 DB를 다시 만든다.
- curl 예시 (`TOKEN`은 로그인 응답의 accessToken):

  curl -s -X PUT localhost:8080/api/members/me/preferences -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \

## 확인 필요
- **구글 서버 장애 시 탈퇴 응답**: 계획서에는 "code exchange fails → 401"이라고 되어 있다. 이 PR은 인가 코드가 거부된 경우(`GOOGLE_AUTH_FAILED`)만 401 `IDENTITY_VERIFICATION_FAILED`로 바꾸고, 구글 5xx·타임아웃은 502 `GOOGLE_SERVER_ERROR` 그대로 둔다. 사용자가 잘못한 게 아니라서 "본인 확인 실패"라고 보여주면 오해를 사기 때문이다.
- **비밀번호 대조 시도 제한**: 비밀번호 변경의 현재 비밀번호와 탈퇴 비밀번호에는 로그인 시도 제한(`LoginAttemptService`)을 걸지 않았다. 둘 다 이미 로그인한 사용자(유효한 액세스 토큰)만 할 수 있다. 필요하면 후속으로 같은 `login:fail:{email}`에 합산할 수 있다.
- **탈퇴 뒤 액세스 토큰**: 탈퇴 후에도 남은 액세스 토큰은 최대 30분 동안 서명 검증을 통과한다. 그 토큰으로 API를 부르면 회원이 없어서 404 "존재하지 않는 회원"이 나간다. 비밀번호 변경 후의 옛 액세스 토큰도 같은 이유로 30분 동안 쓸 수 있다.
- **이름 길이 기준**: 1~30자는 Java 문자열 길이(UTF-16) 기준이다. 이모지는 2자로 센다.
- **`accessible` 컬럼 이름**: 계획의 `accessible` 대신 `accessible_only`를 썼다. MySQL 예약어라서다. ERD에 반영이 필요하다.
