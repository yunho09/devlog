## 작업 내용

### 1. 토큰 재발급 `POST /api/auth/reissue` (rotation)
- 리프레시 토큰을 쓸 때마다 새 액세스 토큰 + 새 리프레시 토큰을 주고, 받은 토큰은 바로 폐기 (`revoked_at` 기록)
  - 새 리프레시 토큰의 유효기간은 지금부터 다시 14일
  - 리프레시 토큰이 유출돼도 한 번 쓰이면 바로 못 쓰게 되고, 아래 재사용 탐지로 이어짐
- 처리 순서 (`TokenService.reissue`)
  1. 해시로 토큰 조회, 없음 → 401 (위조·잘못된 값)
  2. 이미 폐기된 토큰 → **그 회원의 살아 있는 토큰 전부 폐기** 후 401
     - 폐기된 토큰이 다시 왔다는 건 누군가 예전 토큰을 갖고 있다는 뜻. 훔친 사람과 진짜 사용자 중 누가 먼저 썼는지 알 수 없어서 모든 기기를 로그아웃시킴 (명세 설계 메모)
  3. 만료 → 401
  4. 받은 토큰 폐기 + 새 토큰 발급
- 401은 이유와 상관없이 같은 응답(`다시 로그인해주세요.`). FE는 재발급이 401이면 로그인 화면으로 보내면 됨

### 2. `@Transactional(noRollbackFor = CustomException.class)`
- 스프링 트랜잭션은 기본적으로 런타임 예외가 나면 롤백함. 2번에서 "모든 토큰 폐기" UPDATE를 한 뒤 401(`CustomException`)을 던지면, 기본 설정에서는 그 UPDATE까지 롤백돼서 탈취 대응이 사라짐
- `noRollbackFor`로 `CustomException`일 때는 그때까지의 변경을 커밋하게 함
- 이 메서드를 다른 `@Transactional` 메서드 안에서 부르면 바깥 트랜잭션 규칙으로 롤백되므로, 컨트롤러에서 `TokenService`를 바로 부름
- 이 설정을 빼고 테스트를 돌려서, 재사용 탐지 테스트가 실제로 실패하는 것을 확인함

### 3. 동시 재발급 막기 (비관적 락)
- `findByTokenHashForUpdate`: `@Lock(PESSIMISTIC_WRITE)` → MySQL `SELECT ... FOR UPDATE`
- 잠그지 않으면 같은 토큰으로 재발급이 동시에 두 번 왔을 때 둘 다 "아직 폐기 안 됨"을 읽어서 새 토큰을 하나씩 받아감 (rotation이 깨짐)
- 잠그면 두 번째 요청은 첫 번째가 커밋할 때까지 기다렸다가 폐기된 상태를 읽어서 재사용으로 걸림 → 정확히 하나만 성공
- 락을 빼고 동시성 테스트를 돌려서, 둘 다 성공해 테스트가 실패하는 것을 확인함

### 4. 모든 토큰 한 번에 폐기 (`revokeAllActiveByUserId`)
- `@Modifying` JPQL `UPDATE` 한 번으로 그 회원의 `revoked_at IS NULL`인 토큰만 폐기. 이미 폐기된 토큰은 원래 폐기 시각을 유지
- `clearAutomatically = true`: 벌크 UPDATE는 영속성 컨텍스트(1차 캐시)를 거치지 않고 DB에 바로 실행됨. 캐시를 비워서 이후 조회가 바뀌기 전 값을 보지 않게 함
- 비밀번호 재설정(모든 기기 로그아웃)·회원 탈퇴에서도 그대로 쓸 수 있음

### 5. 로그아웃 `POST /api/auth/logout`
- 액세스 토큰 필요 (`SecurityConfig`에서 `/api/auth/**` 중 로그아웃만 인증 필요). `@AuthenticationPrincipal Long userId`로 회원 ID를 받음
- 액세스 토큰만으로는 어느 기기인지 알 수 없어서 body로 이 기기의 리프레시 토큰을 받아 그것만 폐기. 다른 기기의 로그인은 유지
- 토큰이 없거나, 다른 회원의 것이거나, 이미 폐기·만료됐으면 아무것도 하지 않고 똑같이 204
  - 에러로 구분해 주면 남의 리프레시 토큰이 살아 있는지 떠보는 데 쓸 수 있음
  - 같은 요청을 두 번 보내도 결과가 같음 (FE가 재시도해도 안전)

## API 예시

```json
// POST /api/auth/reissue
{ "refreshToken": "Yx3k..." }

// 200 (refreshToken도 새 값. 이전 값은 폐기됐으므로 반드시 바꿔 저장)
{ "accessToken": "eyJhbGciOi...", "refreshToken": "Qm8a..." }

// 401 없음·만료·폐기(재사용) 모두 같음
{ "message": "다시 로그인해주세요.", "status": 401, "timestamp": "...", "description": "만료·폐기·위조된 리프레시 토큰" }

// 400 refreshToken 누락
{ "message": "리프레시 토큰을 입력해주세요.", "status": 400, "timestamp": "...", "description": "refreshToken: 리프레시 토큰을 입력해주세요." }
```

```json
// POST /api/auth/logout
// Authorization: Bearer eyJhbGciOi...
{ "refreshToken": "Qm8a..." }

// 204 (본문 없음)

// 401 액세스 토큰 없음
{ "message": "인증이 필요합니다.", "status": 401, "timestamp": "...", "description": "액세스 토큰 없음" }
```

## 확인 필요
- **로그아웃한 토큰으로 재발급해도 "모든 기기 로그아웃"이 됨**: 로그아웃도 `revoked_at`을 채우는 폐기라서, 로그아웃한 토큰이 다시 오면 재사용(탈취)으로 처리됨. 명세 문구("이미 폐기된 토큰이 다시 들어오면")대로 했고, 로그아웃 전에 토큰을 훔쳐 둔 경우도 막아 줌. 다만 FE가 로그아웃 후 저장된 토큰을 지우지 않고 재발급을 부르면 다른 기기까지 로그아웃되므로 FE에 공유 필요. 구분하려면 폐기 사유 컬럼이 필요함 (ERD에 없음)
- **FE의 동시 재발급**: 탭 여러 개나 동시에 나간 API 요청들이 각자 같은 리프레시 토큰으로 재발급을 부르면, 두 번째부터는 재사용으로 걸려 **모든 기기가 로그아웃됨**. FE에서 재발급 요청을 하나만 보내고 나머지 요청은 그 결과를 기다리게 해야 함. 서버에서 몇 초 유예를 두는 방법도 있지만 명세에 없어서 넣지 않음
- **폐기된 토큰 보관 기간**: 재사용 탐지를 위해 폐기된 행을 지우지 않음. 만료(14일)가 지난 행을 정리하는 배치가 나중에 필요 (명세 미기재)
- **로그아웃 후 액세스 토큰**: 리프레시 토큰만 폐기해서, 이미 발급된 액세스 토큰은 만료(30분)까지 계속 쓸 수 있음. 블랙리스트는 명세에 없어서 넣지 않음
- `refreshToken` 누락은 400으로 처리 (401 아님, 요청 형식 오류로 봄)
