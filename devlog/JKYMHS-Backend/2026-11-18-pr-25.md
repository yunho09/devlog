### 1. 테이블 5개 (`domain/wish/entity`, `domain/behavior/entity`)
| 테이블 | 엔티티 | 키·인덱스 | 왜 |

| `content_views` | `ContentView` | UK `(user_id, content_id, view_date)`, idx `(view_date)`, FK users | 하루 1회만 세기 / 인기 배치가 날짜 범위로 센다 |

- 모든 엔티티는 `Long userId`(+ `contentId`) **숫자 컬럼으로 값을 쓰고**, FK는 `@ManyToOne(insertable = false, updatable = false)` 읽기 전용 연관으로만 만든다. 찜 하나 넣자고 `User`·`Content` 엔티티를 읽지 않아도 되고(쿼리 1개 절약), 콘텐츠 정보는 `ContentService` 한 곳에서만 받는다(도메인 경계).
- `content_views.content_id`, `behavior_events.content_id/trip_id`에는 ERD대로 FK를 걸지 않았다. 통계·이력이라 콘텐츠·여행이 지워져도 남아 있어도 된다.
- `created_at`은 `@CreatedDate` 대신 `Clock`에서 받은 값을 직접 넣는다 (아래 "노션 명세와 다른 점"/계획 대비 차이 참고).

### 2. 찜 API (`domain/wish`)
- `POST /api/wishes/{contentId}`, `DELETE /api/wishes/{contentId}`: **멱등**. 두 번 눌러도 200 + 같은 결과, 찜 수는 실제로 행이 생기거나 지워졌을 때만 ±1 (`ContentService.adjustWishCount`, `GREATEST(wish_count + ?, 0)` 원자적 UPDATE).
- 추가는 `INSERT IGNORE`(`WishRepository.insertIgnore`)로 한 문장에 끝낸다. 리턴값 1 = 새 찜, 0 = 이미 있음. 계획서의 "saveAndFlush 후 `DataIntegrityViolationException` 잡기"는 쓰지 않았다. 저장소(@Transactional) 메서드에서 예외가 나면 바깥 트랜잭션이 rollback-only로 표시돼서, 예외를 잡아도 커밋할 때 `UnexpectedRollbackException`이 난다. 동시에 두 번 눌러도 유니크 키가 막아준다.
- 추가는 삭제된 콘텐츠면 404 `존재하지 않거나 삭제된 장소입니다.`, 삭제는 **삭제된 콘텐츠도 허용**(찜 목록의 "삭제된 장소" 카드에서 지우기)하고 contents에 아예 없는 id만 404 `존재하지 않는 장소입니다.`.
- 새로 찜했을 때만 `BehaviorSignalEvent(WISH)` 발행 → 커밋 뒤 행동 데이터 도메인이 받는다.
- `GET /api/wishes?tab=festival|place&hideEnded&hideClosedToday&cursor&size`
  - `place` = 축제가 아닌 모든 종류(관광지·음식점·숙박, §5 Q18). 정렬은 찜한 시각 desc, 찜 id desc.
  - 카드는 탐색과 같은 `ContentItemResponse`에 `wishedAt`, `deleted`를 붙인 `WishItemResponse` (`@JsonUnwrapped`로 같은 높이에 펼친다 → FE가 같은 카드 컴포넌트를 쓴다). 삭제된 콘텐츠도 `deleted:true`로 넣는다.
  - `hideEnded`(축제): 끝난 축제 제외. `hideClosedToday`(장소): 오늘이 쉬는 날이거나 `openStatus=closed`인 곳 제외.
  - `counts {festival, place}`는 첫 페이지에만, 숨기기 옵션과 무관한 전체 개수.
  - 커서 `{t: 탭, w: 찜한 시각, i: 찜 id}`. 다른 탭의 커서·깨진 커서 → 400 `INVALID_CURSOR`.
  - **구현 방식**: 탭·숨기기 조건이 콘텐츠 정보(종류·축제 기간·운영 시간)에 달려 있는데, 찜 도메인이 contents 테이블과 JOIN하면 "다른 도메인 데이터는 그 Service로만" 규칙을 깬다. 그래서 그 회원의 찜을 모두 읽고(`idx_wishlists_user_id_created_at`), `ContentService.findSnapshots`로 콘텐츠를 한 번에 받아 메모리에서 거르고 자른다. 한 회원의 찜은 많아야 수백 개라 충분하다고 판단했다 (수천 개 회원이 생기면 JOIN 쿼리로 바꿀 것).
- 탈퇴: `WishWithdrawHandler`가 `WithdrawSummaryContributor`(탈퇴 안내의 `wishCount`)와 `UserWithdrawnEvent` 동기 리스너(찜했던 콘텐츠 찜 수 -1 → 찜 삭제)를 함께 맡는다. 회원 행보다 먼저 지워야 FK에 걸리지 않는다.

### 3. 탐색 개인화 (`ContentPersonalizationImpl`)
- D1의 `NoopContentPersonalization`을 지우고 실제 구현을 등록했다 (빈이 두 개면 주입이 충돌한다).

### 4. 행동 데이터·취향 프로필 (`domain/behavior`)
- `BehaviorSignalListener`: `@TransactionalEventListener(AFTER_COMMIT, fallbackExecution = true)` + `@Async("behaviorExecutor")`.
  - AFTER_COMMIT: 찜 추가가 롤백되면 "찜했다"는 행동도 남으면 안 된다.
  - @Async: 동의 확인·저장·180일 재계산을 응답 스레드에서 하지 않는다. 실행기는 `ExecutorFactory.create("behavior", 2, 4, 500)` (`behavior.executor.*`), 테스트(`async.enabled=false`)에서는 동기.
  - fallbackExecution: 트랜잭션 밖에서 발행한 이벤트(D4~D6가 그렇게 할 수 있다)도 버리지 않는다.
- `BehaviorRecorder.record`는 **`REQUIRES_NEW`**. AFTER_COMMIT 리스너가 같은 스레드에서 돌면 끝난 트랜잭션이 아직 스레드에 묶여 있어서, REQUIRED로 참여하면 쓰기가 커밋되지 않고 사라진다.
  - `SCHEDULE_SAVE` → `content_save_logs`는 **동의와 무관하게** 남긴다 (개인 취향이 아니라 전체 통계).
  - `UserConsentService.isAgreed(BEHAVIOR_DATA)`면 `behavior_events` 저장(lcls2·가중치는 저장 시점 값을 복사) → `common` 프로필, 동행이 있으면 그 동행 프로필 재계산.
- `PreferenceProfileService`
  - 점수 = Σ 가중치 × 0.5^(경과일/30), 최근 180일, lcls2별. 시간에 따라 줄어드는 식이라 "기존 점수 + 새 행동"으로 더할 수 없어서 매번 180일치를 다시 더한다 (회원당 수백 건 수준).
  - 쓰기는 `INSERT … VALUES (…) AS new ON DUPLICATE KEY UPDATE`(MySQL 8.0.19+ 문법) + 이번 계산에 없는 lcls2 행 삭제. 같은 회원의 행동 두 개가 동시에 처리돼도 유니크 키 충돌이 없다.
  - **D5 계약**: `getProfile(Long userId, String companion)` → `ProfileView(Map<String,Double> lcls2Scores, int signalCount, boolean companionSpecific)`. 동행 프로필 행동이 10개(`behavior.companion-min-signals`) 미만이면 `common`을 주고 `companionSpecific=false`.
- `BehaviorDataCleaner` (동기 `@EventListener`, 회원 도메인 트랜잭션 안):
  - `BehaviorConsentRevokedEvent` → `behavior_events`, `preference_profiles` 삭제. 조회·담기 기록은 인기 점수용 통계라 남긴다.
  - `UserWithdrawnEvent` → 위 둘 + `content_views`, `content_save_logs` 삭제.

### 5. 인기 점수 배치 (`domain/popularity`)
- `PopularityJob` `@Scheduled(cron = "${popularity.cron:0 0 * * * *}", zone = "Asia/Seoul")` — 매시 정각.
- 원점수(최근 30일) = 조회 × 1 + 새 찜 × 3 + 일정 담기 × 5 → `PopularityScores.normalize`: `round(1000 × ln(1+raw) / ln(1+maxRaw))`. 로그로 펴서 조회가 몰린 몇 곳이 점수를 독차지하지 않게 한다 (§5 Q9). 최고 콘텐츠는 항상 1000점.
- 집계는 각 도메인 서비스로 받는다: `BehaviorStatsService.countViewsSince/countSavesSince`, `WishService.countCreatedSince` (배치가 다른 패키지 테이블을 직접 읽지 않는다).
- `ContentService.updatePopularityScores`가 한 트랜잭션으로 전부 바꾸고(실패하면 롤백 → 이전 점수 유지), **커밋 뒤** `INCR popularity:version`. 그래서 `run()`에는 트랜잭션을 걸지 않았다 (걸면 버전을 올리는 순간 아직 커밋 전이라 "새 버전 + 옛 점수"가 보인다). D1 인기순 커서에는 이 버전이 들어 있어서, 배치 전에 받은 커서로 다음 페이지를 읽으면 409 `CURSOR_VERSION_MISMATCH`.
- Redis가 안 되면 버전만 못 올리고 SUCCESS로 끝난다 (G12: 캐시 장애로 배치를 실패시키지 않는다).
- `batch_job_logs`에 `POPULARITY` 기록, 실패하면 FAILED + `BatchAlertNotifier` 알림.
