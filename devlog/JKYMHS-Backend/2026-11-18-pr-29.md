## 작업 내용

FE의 캘린더 화면(마이페이지 > 캘린더, 여행 업로드 화면, 일괄 업로드 모달)에 필요한 API와, 일정이 바뀌거나 지워질 때 구글 캘린더를 서버가 알아서 맞추는 자동 동기화를 추가했다.
핵심 설계는 **"요청은 할 일(작업)만 DB에 넣고 202, 구글 호출은 작업자가 따로"** 이다.

### 2. 여행 도메인과의 경계 — `TripCalendarSupport` (`domain/trip/service`, 새 파일)

- 캘린더 도메인은 여행 Repository를 직접 쓰지 않는다(컨벤션 §1). 대신 여행 패키지 안의 `TripCalendarSupport`가 유일한 창구다.
- 캘린더 쪽에는 엔티티 대신 값(`CalendarTrip`, `CalendarItem`)만 넘기고, 상태 변경은 의도 메서드(`markPending`/`markSynced`/`markFailed`/`clearEvent`/`clearAll`/`useCalendar`)로만 한다.
- 쓰기 메서드는 부르는 쪽 트랜잭션에 참여한다. 그래서 "작업 행 넣기"와 "항목을 PENDING으로"가 같이 커밋·롤백된다 — 작업은 없는데 PENDING인 항목이 생기지 않는다.
- 작업자가 부를 때는 그사이 항목이 지워졌을 수 있어서, 없는 항목은 조용히 넘어간다.
- 계획에 있던 `CalendarItemStore` 포트 + 빈 구현은 만들지 않았다. 단계(A/B)를 나누지 않았으므로 처음부터 `TripCalendarSupport`를 바로 부른다.

### 3. 리프레시 토큰 암호화 — `CalendarTokenCipher` (AES-256-GCM)

- 리프레시 토큰 = 사용자가 없을 때도 그 사람 캘린더에 쓸 수 있는 열쇠. DB가 유출돼도 키 없이는 못 쓰게 암호화한다.
- GCM을 고른 이유: 암호화와 함께 위·변조 검사(인증 태그)를 해서, DB 값을 누가 바꾸면 복호화가 실패한다.
- 저장 형식 `base64(IV 12바이트 ‖ 암호문+태그)`. IV는 매번 새로 뽑는다(GCM은 같은 키·같은 IV를 두 번 쓰면 안전성이 깨진다). 그래서 같은 토큰도 암호문이 매번 다르다.
- 키 `CALENDAR_TOKEN_ENCRYPTION_KEY`(base64로 32바이트)는 **쓸 때 검사**한다. 비었거나 길이가 틀리면 서버는 뜨고 캘린더만 503. 키 값은 로그에 남기지 않는다(`@Size` 같은 검증도 실패 로그에 값이 찍혀서 쓰지 않았다).
- 연동할 때는 구글 인가 코드(일회용)를 쓰기 **전에** 키부터 확인한다.

### 4. 구글 클라이언트 — `GoogleCalendarClient`

- OAuth(토큰 교환·갱신·폐기·사용자 정보)와 Calendar API v3(캘린더 목록, 일정 추가·조회·수정·되살리기·삭제·이동).
- 오류를 두 갈래로 낸다: 사용자가 기다리는 연동 호출은 `CustomException`(401/502), 작업자·목록 호출은 `GoogleAuthExpiredException`(invalid_grant) / `GoogleApiException`(상태 코드). 부르는 쪽이 상태 코드로 "다시 시도 / 실패 / 재연동"을 고른다.
- 구글은 사용량 초과를 429뿐 아니라 **403 `rateLimitExceeded`** 로도 준다. 이 경우는 "쓰기 권한 없음"이 아니라 다시 시도로 본다.
- `calendarId`에 `@`·`#`이 들어가서(`ko.south_korea#holiday@group.v.calendar.google.com`) 주소를 문자열로 잇지 않고 URI 템플릿 변수로 넘긴다(RestClient가 인코딩).
- 타임아웃 5초(`google-calendar.timeout`).

### 5. 연동·상태·캘린더 목록·기본 캘린더·해제 — `CalendarLinkService`

- **클래스 단위 `@Transactional`을 두지 않았다.** 구글 응답을 기다리는 동안 DB 커넥션을 쥐고 있지 않게, 구글 호출은 트랜잭션 밖에서 하고 DB 쓰기만 `TransactionTemplate`으로 짧게 묶는다. 특히 "토큰 만료 → REVOKED로 바꾸고 401"은 예외를 던져도 REVOKED가 커밋돼야 해서 바깥 트랜잭션이 있으면 안 된다.
- 연동: 인가 코드 → 토큰 → **권한 확인**(`calendar.events`, `calendar.calendarlist.readonly` 둘 다) → **리프레시 토큰 확인**(동의 화면을 `access_type=offline&prompt=consent`로 열어야 온다) → 이메일 → 저장. 이미 연동돼 있으면 같은 행을 새 토큰으로 바꾸고 ACTIVE로. 다른 구글 계정이면 예전 계정의 캘린더 id를 못 쓰니 기본 캘린더를 `primary`로 되돌린다.
- 캘린더 목록: `accessRole`이 owner·writer인 것만(공휴일·구독 캘린더 제외). 사용자가 붙인 이름(`summaryOverride`)이 먼저.
- 해제 `deleteEvents=false`: 연동 행 삭제 + 항목·여행의 캘린더 정보 비움 → 커밋 뒤 토큰 폐기(실패해도 무시). 구글 쪽 일정은 남는다.
- 해제 `deleteEvents=true`: `DELETE_ALL` 작업(토큰 사본 + `revoke_after=1`)만 넣고 202. 연동 행은 **작업이 끝날 때** 지운다. 그사이 다시 연동했으면(연동 행의 암호문이 작업의 사본과 다르면) 새 연동은 건드리지 않고 예전 토큰도 폐기하지 않는다(같은 구글 계정이면 폐기가 새 연동까지 끊을 수 있어서).

### 6. 업로드·일괄 업로드·실패만 다시·진행 상태 — `CalendarUploadService`, `CalendarJobService`

- 할 일 정하기 `CalendarJobOp.upsert(item, calendarId)`: 올린 적 없으면 CREATE, 다른 캘린더에 있으면 MOVE, 같은 캘린더면 UPDATE.
- 업로드 기본값(`itemIds` 없음) = 확정안에서 `synced`가 아닌 항목 전부(FE 기본 선택과 같다). 캘린더 기본값 = 요청값 → 이 여행이 마지막으로 쓴 캘린더 → 연동의 기본 캘린더.
- 고른 캘린더가 이 여행이 쓰던 것과 다르면, **이미 올라간 나머지 일정도 같은 작업에서 MOVE** 한다(한 여행이 두 캘린더에 흩어지지 않게, PRD).
- **회원당 사용자 작업(UPLOAD·BULK_UPLOAD) 하나** → 409 `CALENDAR_SYNC_IN_PROGRESS`, `description`에 진행 중인 작업 id. "확인하고 넣기" 사이에 같은 회원의 두 요청이 끼어들지 않게 **연동 행을 `PESSIMISTIC_WRITE`로 잠가** 한 줄로 세운다(작업 테이블에는 잠글 행이 아직 없어서). 자동 작업(SYNC·DELETE_*)은 막지도 막히지도 않는다.
- 일괄 업로드: 10개 초과는 `@Size`가 아니라 서비스에서 400 `SCHEDULE_LIMIT_EXCEEDED`("한 번에 최대 10개 여행까지 올릴 수 있습니다.") — code가 INVALID_INPUT이면 안 돼서. 확정 전 여행은 `NOT_CONFIRMED`, 올릴 게 없으면 `ALREADY_SYNCED`로 건너뛴다. 지난 여행도 된다.
- 실패만 다시: 끝난 작업의 FAILED 항목만 새 작업으로. 할 일은 **지금 항목 상태로 다시 정한다**(그사이 지워졌으면 빼고, 다른 작업이 먼저 올렸으면 UPDATE).
- 할 일이 0개인 작업(모두 건너뜀 등)은 만들자마자 DONE이다.
- 진행 상태: `failedItems`(이름·시각 라벨·이유 코드·화면 문구), 여행별 `succeeded/total`, `retryable`, 끝나면 `pollAfterMs` 필드 자체가 빠진다(`@JsonInclude(NON_NULL)`). 남의 작업도 404(작업 id로 남의 작업이 있는지 알 수 없게).

### 7. 작업자 — `CalendarSyncWorker` / `CalendarJobProcessor` / `CalendarJobStore`

```
@Scheduled 2초 → SELECT … FOR UPDATE SKIP LOCKED LIMIT 5 → RUNNING + 임대 5분 → calendarExecutor
  → 액세스 토큰(리프레시 토큰 grant) → 항목 최대 50개를 하나씩 → 결과마다 바로 기록 → 남으면 다음 차례 / 다 끝나면 마무리
```

- **`FOR UPDATE SKIP LOCKED`**: 서버가 여러 대일 때 다른 서버가 잠근 행은 기다리지 않고 건너뛴다. 같은 작업을 두 서버가 처리하지 않는다. JPQL에는 없어서 네이티브 쿼리.
- **임대(lease)**: 집은 작업은 `RUNNING` + `next_attempt_at = 지금 + 5분`. 작업자가 처리 중에 죽으면 5분 뒤 다시 집힌다(작업이 RUNNING에 영원히 멈추지 않게). 계획에 없던 장치라 설정 `google-calendar.lease`를 추가했다.
- 실행기를 따로(`calendarExecutor`) 두는 이유: 일정 50개를 차례로 올리면 수십 초가 걸릴 수 있다. 스케줄러 스레드에서 돌리면 다른 `@Scheduled` 배치가 밀린다. 실행기가 꽉 차면(TaskRejected) 작업을 PENDING으로 되돌린다.
- **구글 호출은 트랜잭션 밖**, 결과 하나마다 `CalendarJobStore`의 짧은 트랜잭션으로 "작업 항목 상태 + 일정 항목 SYNCED/FAILED"를 같이 기록한다. 중간에 죽어도 끝난 항목은 다시 하지 않는다.
- 오류 처리:
  - `invalid_grant` → 연동 REVOKED, 남은 항목 `AUTH_EXPIRED`, 작업 FAILED
  - 429·5xx·응답 없음(·403 rateLimit) → 항목 시도 +1, 작업을 `5초 × 2^(시도-1)` 뒤로 미루고 이번 차례 중단(사용량 제한일 때 바로 다음 항목을 부르면 또 거절당하니까). 3번째면 그 항목 `GOOGLE_ERROR`
  - 403 → `NOT_WRITABLE`, 그 밖의 4xx → `GOOGLE_ERROR` (그 항목만)
  - 최종 DONE(실패 0) / FAILED(성공 0) / PARTIAL_FAILED
- 일정 id = `"edgl" + 일정 항목 id`. 구글은 우리가 정한 id(base32hex)를 받는다 → 같은 항목을 두 번 올려도(재시도·중복 클릭) 409로 막혀서 일정이 둘이 되지 않고, 삭제 작업에서 일정 id만 보고 항목을 되찾을 수 있다.
- 추가 409 → 그 일정을 읽어서 `cancelled`(지운 일정, 구글이 id를 한동안 붙잡고 있음)면 `PATCH status=confirmed`로 되살리고, 아니면 PUT. 수정 404/410 → 새로 추가. 삭제 404/410 → 성공.
- **할 일은 작업 항목의 operation보다 "지금 항목 상태"를 따른다.** 작업이 기다리는 동안 다른 작업이 먼저 올렸거나 옮겼어도 결과가 맞게 하기 위해서다.
- 일정 내용: 제목 `[어디 갈래] {이름}`, 장소 = 주소, 설명 = 메모 + `{FRONTEND_BASE_URL}/places/{contentId}`, 시작 시각이 없으면 종일(끝 날짜는 다음 날 — 구글 규칙), 끝 시각이 없으면 머무는 시간(없으면 1시간), 자정을 넘기면 다음 날. 시각은 `Asia/Seoul`.
- 처음 만든 일정마다 `BehaviorSignalEvent(CALENDAR, 가중치 5)`를 **트랜잭션 안에서** 낸다(받는 쪽이 트랜잭션 이벤트 리스너여도 받게).
- 마무리: `revoke_after`면 토큰 폐기 + 연동 삭제(5번 참고) → 이 작업이 다룬 여행마다 남은 DIRTY를 다시 맞춘다(아래 8번).

### 8. 자동 동기화 — `CalendarAutoSyncListener` / `CalendarAutoSyncService`

| 이벤트 (#26이 발행) | 받는 방법 | 하는 일 |
|---|---|---|
| `ConfirmedPlanChangedEvent` (확정안 저장·장소 담기·여행 날짜 변경) | `@TransactionalEventListener(AFTER_COMMIT)` + `REQUIRES_NEW` | 올린 여행이면 SYNC: 올라간 항목 중 SYNCED가 아닌 것 → UPDATE, 아직 안 올라간 항목(NONE) → CREATE |
| `ConfirmedPlanSwitchedEvent` (확정안 교체) | 동기 `@EventListener` (같은 트랜잭션) | 예전 확정안 일정 DELETE + 새 확정안 항목 CREATE |
| `CalendarEventsOrphanedEvent` (여행·일정안 삭제, 저장에서 빠짐, 기간 축소) | 동기 | DELETE_EVENTS |
| `UserWithdrawnEvent` | 동기, `@Order(HIGHEST_PRECEDENCE)` | DELETE_ALL(토큰 사본·끝나면 폐기) + 연동 행 삭제(벌크 DELETE) |

- 저장 이벤트를 **커밋 뒤에** 받는 이유: 커밋 전에 작업을 넣으면 작업자가 아직 커밋 안 된 옛 값을 읽을 수 있고, 저장이 롤백돼도 작업이 남을 수 있다. 이 단계의 예외는 이미 커밋된 저장 요청을 500으로 만들기 때문에 잡아서 로그만 남긴다.
- 교체·삭제 이벤트를 **같은 트랜잭션에서** 받는 이유: 행이 지워진 뒤에는 어느 일정을 지워야 하는지 알 수 없고, 삭제가 롤백되면 작업도 같이 사라져야 한다.
- 연동이 ACTIVE일 때만 작업을 만든다(만료·해제 상태에선 구글에 접근할 수 없다).
- **같은 여행에 진행 중인 작업이 있으면 SYNC를 만들지 않는다.** 대신 작업자가 그 작업을 끝낼 때 남은 DIRTY를 다시 맞춘다. 예: 저장에서 한 항목을 빼고 다른 항목 시간을 바꾸면 → 같은 트랜잭션에서 DELETE_EVENTS가 먼저 들어가고 → 커밋 뒤 SYNC는 미뤄지고 → DELETE가 끝나면 SYNC가 생긴다.
- 탈퇴 리스너가 **가장 먼저** 도는 이유: 여행 탈퇴 리스너가 여행을 지우기 전에 "올린 일정 목록"을 읽어야 한다. 이어서 여행 리스너가 내는 `CalendarEventsOrphanedEvent`는 연동 행이 이미 없어서 작업을 만들지 않는다 → 같은 일정을 지우는 작업이 두 개 생기지 않는다.
- 연동 행은 `em.remove`가 아니라 벌크 DELETE로 지운다(#26의 탈퇴 정리와 같은 이유 — 회원 엔티티 remove 때 참조 오류).
- 탈퇴 요약 `calendarEventCount` = 지금 구글에 올라가 있는 일정 수(`CalendarWithdrawSummaryContributor`).

## 확인 필요

- **자동 동기화의 CREATE 범위**: 한 번이라도 올린 여행이면 확정안에서 아직 안 올라간(NONE) 항목을 모두 CREATE 한다(계획의 "new items → CREATE"). 업로드 화면에서 일부러 뺀 항목도 다음 저장 때 올라간다. "업로드 뒤 새로 담은 장소만"으로 좁히려면 항목에 "제외" 표시를 따로 저장해야 한다 — 기본값(전부 올림)으로 진행.
- **PENDING 중 수정**: 항목이 작업에서 기다리는(PENDING) 동안 또 수정하면 `markDirty`가 SYNCED에서만 동작해서 DIRTY가 되지 않는다. 작업자는 처리 시점의 최신 값으로 올리므로 대부분 맞지만, 구글 호출 직후·기록 직전에 저장이 끼면 그 변경은 다음 수정 때까지 반영되지 않는다.
- 자동 SYNC 중복: 두 저장이 거의 동시에 커밋되면 같은 여행에 SYNC가 두 개 생길 수 있다(결과는 같고 호출만 늘어남). 잠금을 걸지 않았다.
- 실패한 새 항목(FAILED, 일정 없음)은 자동으로 다시 올리지 않는다(사용자가 "다시 시도"·업로드로 올린다).
- 업로드할 캘린더의 쓰기 권한은 요청 시 확인하지 않는다(구글 호출이 필요해서). 쓸 수 없으면 작업자가 항목을 `NOT_WRITABLE`로 실패시킨다.
- 작업 행·작업 항목 행은 지우지 않고 쌓인다. 오래된 작업 정리 배치는 이 PR에 없다.
