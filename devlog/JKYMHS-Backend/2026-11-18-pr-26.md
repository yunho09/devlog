## 작업 내용

### 1. 테이블 (`domain/trip/entity`) — 여행 → 일정안 → 일정 항목
- `trips`: 여행 하나. `confirmed_plan_id`가 확정 일정안이다. 여기에 FK를 걸지 않은 이유는 `plans.trip_id → trips`와 서로를 가리키게 되면 만들 때(일정안이 아직 없음)·지울 때 어느 쪽도 먼저 넣거나 지울 수 없기 때문이다. 일정안을 지우면 앱에서 null로 바꾼다.
  - 인덱스 `(user_id, start_date, id)`는 여행 목록 커서 정렬용, `(user_id, end_date, id)`는 "다가오는/지난" 구분과 방문 확인 대상 찾기용이다.
  - `version` 컬럼(G10): `@Version` 대신 직접 비교한다. `@Version`의 충돌 예외는 핸들러가 409로 바꾸지 않기 때문이다.
- `trip_regions`(여행 지역 1~5개), `plans`(일정안, `source` AI/AI_RETRY/MANUAL, `total_move_minutes`·`version`), `plan_items`(장소 하나), `visit_reviews`(방문 확인, `plan_item_id` UNIQUE).
- `plan_items.snapshot_*`: 담을 때의 장소 이름·주소·사진·좌표를 복사해 둔다. TourAPI에서 장소가 내려가도(소프트 삭제) 일정은 그대로 보여야 하고, 일정 화면마다 contents를 다시 읽지 않아도 되게 하려고.
- `plan_items`의 이동 컬럼(`transport_mode`, `travel_minutes`, `route_polyline` …)은 "앞 장소(첫째 날 첫 장소는 출발지)에서 이 장소로 오는" 이동이다.
- 캘린더 컬럼(`calendar_event_id`, `sync_status` NONE/DIRTY/PENDING/SYNCED/FAILED)은 #D6(캘린더)가 쓴다. 이 PR은 의도 메서드만 준비했다: `PlanItem.markDirty()/markPending()/markSynced(calendarId, eventId, now)/markFailed()/clearCalendar()`, `Trip.useCalendar(String)`.
- FK는 `Content`가 지역 FK에 쓴 방식과 같다: id는 `Long` 컬럼으로 읽고 쓰고, `insertable=false, updatable=false`인 `@ManyToOne`은 FK 제약을 만들기 위해서만 둔다 (다른 도메인 엔티티를 불러오지 않고도 FK가 생긴다).

### 2. 여행 API (`TripService`, `TripListService`)
- `POST /api/trips`: 여행 + 빈 "기본 코스"(MANUAL) 일정안을 만들고 확정한다 (FE는 여행에 항상 확정안이 있다고 가정한다). 기간 14일, 지역 1~5개, 아이와 가면 나이 필수. 날짜 순서·기간·아이 나이처럼 필드끼리의 규칙은 상황별 문구가 달라서 서비스에서 `CustomException(code, message, description)`으로 던진다.
- `GET /api/trips`: 다가오는 여행(종료일 ≥ 오늘, 진행 중 포함)을 시작일 순으로 먼저, 지난 여행을 시작일 역순으로. 두 묶음은 정렬 방향이 달라서 쿼리 하나로 커서를 만들 수 없다 → 다가오는 쪽을 먼저 읽고 한 페이지가 덜 차면 지난 쪽에서 이어 채운다. 커서 `{f: 필터, g: 묶음, d: 시작일, i: id}`라서 다른 필터의 커서를 넣으면 400 `INVALID_CURSOR`.
  - 카드에 필요한 지역·일정안·장소·방문 확인은 페이지의 여행 id로 한 번씩만 모아 읽는다 (여행마다 쿼리를 날리는 N+1을 피했다).
  - `counts`·`visitCheckPending`은 첫 페이지에서만 채운다.
- `GET/PATCH/DELETE /api/trips/{id}`, `POST /api/trips/{id}/copy`, `GET /api/trips/targets`.
  - PATCH에서 기간을 줄여 장소가 빠지면 422 `PLAN_EXCEEDS_TRIP_PERIOD`(description = 빠질 장소 수)로 먼저 묻고, `removeOutOfRangeItems: true`면 지운다. 가는 날을 옮기면 캘린더에 올린 확정안 항목을 DIRTY로 바꾸고 `ConfirmedPlanChangedEvent`를 낸다 (캘린더 일정 날짜가 모두 달라지므로).
  - DELETE는 캘린더 정리 이벤트를 먼저 내고(지운 뒤에는 event id를 읽을 수 없다) FK 순서대로 방문 확인 → 항목 → 일정안 → 지역 → 여행을 DELETE 문으로 지운다.
- 다른 회원의 여행은 403, 없는 여행은 404 "존재하지 않는 여행입니다." (`TripAccess`가 한곳에서 확인).

### 3. 일정안 API (`PlanService`)
- 추가·복제·이름 변경·삭제·확정. 일정안 10개 제한, 마지막 일정안 삭제 409, 확정안을 지우면 확정이 풀린다.
- **잠금:** 쓰기는 모두 여행 행을 먼저 `PESSIMISTIC_WRITE`로 잠그고 시작한다. 같은 여행의 일정안 수·확정안·장소 목록을 두 요청이 동시에 바꾸면 "일정안 11개" 같은 상태가 생길 수 있어서 여행 단위로 줄을 세웠다. 잠그는 순서를 항상 여행 → 일정안으로 맞춰서 교착을 피한다.
- **전체 저장 `PUT /api/trips/{id}/plans/{planId}`:** 버전 비교(다르면 409) → 검증 → itemId로 비교해서 수정/추가/삭제 → 날짜별 순서 1..n → 앞 장소가 바뀐 항목만 이동을 다시 정함 → 이동 시간 합계·버전 +1.
  - 남아 있는 항목은 id를 유지한다. 구글 캘린더 eventId를 항목 id로 만들기 때문이다.
  - 이동은 외부 API를 부르지 않고 Redis 경로 캐시(FE가 미리 부른 `POST /api/routes` 결과) → 없으면 직선거리 어림값(`isEstimated: true`)으로 채운다 (§5 Q12). 여행 행을 잠근 채 외부 응답을 기다리면 같은 여행의 다른 요청이 모두 밀리기 때문이다.
  - 캘린더에 올린 항목의 장소·날짜·순서·시간·메모가 바뀌면 DIRTY, 빠진 항목은 `CalendarEventsOrphanedEvent`, 확정안이면 `ConfirmedPlanChangedEvent`, 새로 넣은 장소만 `BehaviorSignalEvent(SCHEDULE_SAVE)`.
- **상세 `GET …/plans/{planId}`:** 여행 기간의 모든 날을 내려주고 항목마다 경고를 계산한다 (`PlanWarning`: 점심·저녁 시간, 입장 마감 후, 닫은 뒤, 쉬는 날, 축제 기간 밖). 경고는 저장하지 않고 읽을 때 지금 콘텐츠 정보로 계산한다 — 운영 정보는 매일 동기화로 바뀌어서 저장하면 금방 낡는다.
- **담기 `POST …/plans/{planId}/items`:** 그날 마지막에 붙이고 앞 장소에서 오는 이동을 채운다. 같은 날 같은 장소 409(`allowDuplicate`로 우회), 지난 여행 422, 30개 제한.
- 확정 변경 `PUT /api/trips/{id}/confirmed-plan`은 예전 확정안의 캘린더 일정을 담아 `ConfirmedPlanSwitchedEvent`를 낸다.

### 4. 경로 계산 (`domain/route`)
- `POST /api/routes`: 구간 1~30개를 한 번에 계산한다.
- 규칙: 직선 ≤1000m(아이·부모님 ≤500m) → 도보(분당 67m), 외부 API 안 부름 → Redis 캐시(7일) → ODsay 대중교통 + 카카오모빌리티 택시를 **동시에** 부름(`routeExecutor`) → 대중교통 ≤ 1.5 × 택시면 대중교통(대안 택시), 아니면 택시(대안 대중교통). 한쪽만 결과가 있으면 그쪽만, 둘 다 실패하면 직선거리 어림값(캐시하지 않음 — 다음에 외부 API가 살아나면 제대로 계산하게).
- 외부 API 실패는 예외 대신 빈 결과로 처리해서 502를 내지 않는다 (일정 화면이 막히지 않게). ODsay는 오류도 HTTP 200 + `{"error": …}`로 주는 경우가 많아서 본문을 보고 판단한다.
- 도보 결과를 캐시하지 않는 이유: 같은 구간이라도 동행에 따라 도보 여부가 달라서(500m/1000m) 좌표만으로 만든 키에 넣으면 섞인다.
- 구간 여러 개는 모든 외부 호출을 한꺼번에 실행기에 넣고 마지막에 모은다. "작업 안에서 또 작업을 기다리면" 스레드가 모두 기다리는 쪽에 묶여 멈출 수 있어서다.
- polyline: 택시는 카카오 `vertexes`(실제 도로), 대중교통·도보·어림값은 출발→도착 직선 (§5 Q13). 구글 encoded polyline(정밀도 5).
- Redis 장애 시 캐시만 건너뛴다 (G12).
- `RouteService`는 AI 추천(D5)이 쓰는 계약이다: `route(from, to, companion)`, `routes(segments, companion)`, `estimate(from, to)`, `cached(from, to)`, 그리고 `routeWithoutExternal(from, to, companion)`(도보 → 캐시 → 어림값).

### 5. 방문 확인 (`VisitCheckService`, `VisitCheckMailJob`)
- 대상: 끝났고, 확정안에 장소가 있고, DONE/DISMISSED가 아니고, "나중에"로 미룬 날이 지났고, 행동 데이터 수집에 동의함. 배너는 가장 최근에 끝난 대상 여행이고, 처음 대상이 될 때 PENDING이 된다.
- 저장은 부분 저장이다. 모두 답하면 DONE. 처음 답한 장소만 만족도별 행동 신호(4~5 만족, 3 보통, 1~2 불만족)를 낸다 — 고쳐도 다시 내지 않아서 같은 방문이 두 번 세지지 않는다. FE는 "안 감"에 rating 0을 보내서 0도 받고 null로 저장한다 (§5 Q27).
- "나중에": 첫 번째는 3일 뒤 다시, 두 번째는 DISMISSED.
- 메일 배치(매일 10:00 KST): 행동 데이터 + 이메일 알림 동의 회원에게만, 여행당 한 번. 여행마다 "보냄" 표시를 따로 커밋해서 중간에 SMTP가 실패해도 이미 보낸 여행에 또 보내지 않는다. 발송은 트랜잭션 밖에서 한다(DB 연결을 쥔 채 SMTP를 기다리지 않게). 실행 기록은 `batch_job_logs`(`VISIT_CHECK_MAIL`).

### 6. 다른 도메인과의 연결
- **탈퇴:** `TripWithdrawListener`가 `UserWithdrawnEvent`를 같은 트랜잭션에서(동기 `@EventListener`) 받아 캘린더 정리 이벤트를 낸 뒤 여행 데이터를 모두 지운다. `TripWithdrawSummaryContributor`가 탈퇴 요약의 `tripCount`·`planCount`를 채운다.
- **삭제를 DELETE 문으로 하는 이유:** 처음에는 엔티티를 불러와 `remove`했는데, 같은 트랜잭션에 그 여행을 가리키는 일정안 엔티티가 남아 있으면 Hibernate가 flush 때 `TransientPropertyValueException`으로 실패했다 (탈퇴에서는 회원 도메인이 이어서 회원을 remove할 때 같은 문제가 생긴다). 그래서 id만 읽고 DELETE 문으로 지운다 (후속 커밋 `fix:`).
- **이벤트(`domain/trip/event`, D6가 받음):** `ConfirmedPlanChangedEvent`(저장 트랜잭션 안에서 발행 — 받는 쪽은 `@TransactionalEventListener(AFTER_COMMIT)`), `ConfirmedPlanSwitchedEvent`·`CalendarEventsOrphanedEvent`(행을 지우기 전에 발행 — 받는 쪽 동기 리스너가 같은 트랜잭션에서 작업 행을 넣는다).
- **AI 추천(D5) 계약:** `TripService.createTripWithPlan(userId, NewTripCommand, PlanDraft)`, `addPlan(userId, tripId, PlanDraft, makeConfirmed)`, `getOwnedTrip(userId, tripId)`.

## 직접 확인할 것
- `.env`에 키 추가 (없으면 서버는 뜨고 대중교통·택시 대신 어림값으로 답한다):
  - `KAKAO_REST_API_KEY=` — 카카오 디벨로퍼스 REST API 키 (카카오 로컬과 같은 키). 앱 설정에서 **카카오내비(모빌리티) API 사용 설정**이 켜져 있어야 한다.
  - `ODSAY_API_KEY=` — ODsay LAB **서버용** 키. 등록한 서버 IP에서만 동작하므로 로컬 PC의 공인 IP를 등록해야 한다.
  - `FRONTEND_BASE_URL=` — 방문 확인 메일 링크 주소 (기본 `http://localhost:3000`).
- 실행 후 확인 (`TOKEN`은 로그인 응답의 accessToken):
  ```bash
  curl -s -X POST localhost:8080/api/routes -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
    -d '{"segments":[{"from":{"lat":37.5796,"lng":126.9770},"to":{"lat":37.5547,"lng":126.9707}}]}'
  # isEstimated:false 이고 mode가 transit/taxi면 외부 API 연결 성공. 같은 요청을 다시 보내면 Redis 캐시(route:*)에서 나온다
  docker compose exec redis redis-cli --scan --pattern 'route:*'

  curl -s -X POST localhost:8080/api/trips -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
    -d '{"title":"테스트","startDate":"2026-11-20","endDate":"2026-11-21","regionIds":[1],"companion":"friends"}'
  curl -s localhost:8080/api/trips -H "Authorization: Bearer $TOKEN"
  ```

## 확인 필요
- **D6(캘린더) 연결:** 이벤트 3종은 발행만 하고 아직 받는 쪽이 없다. `ConfirmedPlanChangedEvent`는 트랜잭션 안에서 발행하므로 D6는 `@TransactionalEventListener(AFTER_COMMIT)`로 받아야 저장이 롤백될 때 동기화하지 않는다.
- **ODsay polyline:** 대중교통 경로는 직선으로 그린다 (`loadLane` 미호출, §5 Q13). 실제 노선 모양이 필요하면 후속으로.
- **진행 중 여행:** 종료일 ≥ 오늘이면 "다가오는 여행"으로 묶었다 (FE trips-page 기준). FE가 진행 중을 따로 보여주려면 `group`에 값 추가가 필요하다.
- **기간 축소 422의 description:** 계획대로 지워질 장소 수(문자열 "2")를 넣었다. FE 문구가 확정되면 맞춘다.
- **메일 대상 7일 제한**은 계획에 없던 값이다 (위 "세부 결정"). 필요 없으면 `visit-check.mail-lookback-days`를 늘리면 된다.
