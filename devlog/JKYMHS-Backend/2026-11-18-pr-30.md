## 작업 내용

### 1. 테이블 (`domain/recommendation/entity`)
- `recommendation_requests` (`RecommendationRequest`): 추천 요청 한 건. 결과(코스 3개)는 Redis에 24시간만 두고, 이 행은 **하루 횟수 계산과 조건 기록**에 쓴다.
  - `requested_at` 컬럼을 계획보다 하나 더 뒀다. `created_at`은 JPA Auditing이 시스템 시계로 채워서 테스트의 고정 시계(`Clock`)를 따르지 않는다. 중복 요청 판정(10초)·만료(24시간)·정리 배치가 모두 이 시각을 기준으로 해서 `Clock`으로 직접 넣는다.
  - `conditions_key`(SHA-256)도 추가했다. "같은 조건으로 10초 안에 다시 온 요청"을 찾을 때 지역·꼭 포함 장소 같은 자식 행까지 불러와 비교하지 않고 키 하나로 찾으려는 것이다.
  - 인덱스: `(user_id, request_date, status)` — 오늘 횟수 세기, `(status, requested_at)` — 정리 배치가 멈춘 PENDING을 찾을 때.
  - `user_id`/`sido_region_id`는 값(Long)으로 읽고 FK만 `@ManyToOne(insertable=false, updatable=false)`로 건다 (D4 `Trip`과 같은 방식). 다른 도메인 엔티티를 불러오지 않아서 지연 로딩 문제가 없다.
  - `target_trip_id`, `previous_request_id`는 FK 없음: 여행이 지워져도 추천 기록은 남아야 한다.
  - 출발지 좌표·주소는 NULL 가능으로 바꿨다 (24시간 뒤 정리 배치가 지운다, §5 Q11).
- `recommendation_request_regions`(고른 시·군·구), `recommendation_required_places`(꼭 포함할 장소, 순서), `travel_style_mappings`(여행 스타일 → 분류 코드). 매핑은 `TravelStyleMappingSeeder`가 서버 시작 때 채운다 (몇 번 돌려도 같은 결과).

### 2. 요청 흐름 (`RecommendationService`)
- **검증 → (트랜잭션) 회원 행 잠금 → 중복 확인 → 횟수 확인 → PENDING 저장 → 커밋 → 실행기에 작업 → 202.**
- `UserService.getByIdForUpdate`로 회원 행을 `SELECT … FOR UPDATE` 한다. 같은 회원이 동시에 두 번 눌러도 "센 다음 넣기"가 겹치지 않아 10회를 넘기지 않는다.
- 작업은 **커밋한 뒤** 실행기에 넣는다. 커밋 전에 넣으면 작업 스레드가 아직 보이지 않는 행을 읽을 수 있다. 그래서 서비스 메서드에 `@Transactional`을 걸지 않고 `TransactionTemplate`으로 저장 부분만 묶었다.
- 실행기(`recommendationExecutor`, 4/8/50)가 가득 차면 `TaskRejectedException` → 요청을 FAILED(`AI_UNAVAILABLE`)로 바꾸고 503. 무한정 쌓아 두면 사용자가 30초 넘게 기다리게 된다.
- **횟수** = 오늘(KST) 요청 중 FAILED가 아닌 것. 기본 코스(FALLBACK)도 결과를 받았으니 센다. 실패는 세지 않으므로 "돌려주기"를 따로 하지 않아도 된다.
- **중복 방지**: FE는 5xx 뒤 한 번 재시도한다. 같은 조건의 PENDING이 10초 안에 있으면 새로 만들지 않고 그 requestId를 준다.
- 꼭 포함할 장소가 기간·지역에 안 맞으면 막지 않고 `warnings`로만 알린다. 없는 장소는 404.
- `targetTripId`는 `TripService.getOwnedTrip`으로 403/404를 확인한다.

### 3. 작업 (`RecommendationWorker`, 실행기 스레드)
단계마다 Redis `rec:progress:{id}`를 고쳐서 FE polling이 진행 화면을 그린다.
1. **CANDIDATES** (`CandidateService`): 지역·기간이 같은 요청이 같이 쓰는 인기 순 200곳을 `candidates:{sido}:{districts|all}:{start}:{end}`에 1시간 캐시한다 (id만). **회원 점수는 캐시에 넣지 않는다**: 인기×0.4 + 취향 프로필(D3 `PreferenceProfileService`, 최대값으로 −1~1 정규화)×0.4 + 여행 스타일 일치×0.2 + 실내 선호 ±0.15 − 뺄 곳 0.5. 반려동물과 가면 동반 불가로 확인된 곳은 뺀다. 상위 40곳 + 꼭 포함 장소. 하루 2곳도 안 되면 FAILED(`NOT_ENOUGH_CANDIDATES`). Redis가 죽으면 캐시 없이 DB에서 읽는다.
2. **COMPOSE**: `AiCourseClient.compose` → 코스 3개.
3. **HOURS** (`CourseValidator`): AI 응답을 그대로 믿지 않는다. 코스 수·날짜 모양, 후보에 없는 id, 중복, 빠진 꼭 포함 장소, 하루 장소 수(여유 2~3 / 빡빡 4~5 / 아이 −1), 축제 기간, 쉬는 요일, 영업시간, 아이와 가면 20:00 넘어 끝나는 장소. 영업시간은 직선거리 어림 이동으로 만든 임시 시각으로 본다 (외부 경로 API는 검증을 통과한 코스에만 부른다). 위반이 있으면 그 문장 목록을 `violations`로 붙여 **한 번 더** 요청하고, 또 어기거나 AI 오류·시간 초과면 `FallbackCourseBuilder`의 "기본 추천 코스"(FALLBACK). 꼭 포함 장소는 사용자가 고른 곳이라 기간·요일·영업시간 검사에서 뺀다.
4. **ROUTES** (`CourseAssembler`): 코스 3개의 모든 구간을 모아 중복을 빼고 D4 `RouteService.routes` 한 번으로 계산한다 (도보 ≤1km/아이·부모님 500m, 캐시 7일, ODsay·카카오 동시 호출). 둘째 날 출발점은 전날 마지막 장소다.
5. **MEALS** (`CourseTimeline`): 시각을 "0시부터의 분"(int)으로 계산해서 자정을 넘겨도 값이 돌아가지 않게 했다. 앞 장소가 11:30~12:30 사이에 끝나면 점심 60분, 17:30~18:30이면 저녁. 창이 열리기 1시간 전 이내인데 다음 장소를 다녀오면 시작 가능 시각을 넘기면 창 시작 시각에 먼저 넣는다 (점심을 건너뛰지 않게). 식사 칸의 `nearbyRestaurantCount`는 앞 장소 1km 안의 음식점 수 (`ContentNearbyService.countWithin`, 반경을 넓히지 않는 새 메서드).
6. 결과를 `rec:result:{id}`(24시간)에 저장 → DONE/FALLBACK. 결과 저장 실패는 FAILED(`INTERNAL`): 결과는 "꼭 남아야 하는 값"이라 Redis 오류를 숨기지 않는다 (G12).
- 상태 변경은 `UPDATE … WHERE status = 'PENDING'` 한 문장이다. 작업이 끝나는 순간과 정리 배치가 겹쳐도 한쪽만 이긴다.
- 전체 제한 시간 25초가 지나면 AI 재요청과 외부 경로 API를 건너뛴다 (FE가 최대 30초 기다린다).

### 4. AI 클라이언트 (`client/ai`)
- `ai.provider=mock`(기본): `MockAiCourseClient`. AI 서버 계약이 확정되기 전에도 FE가 추천 화면 전체를 붙여 볼 수 있다. 점수 순 후보를 출발지에서 가까운 순으로 하루씩 채우고(`NearestCoursePlanner`), 기본 코스도 같은 알고리즘을 쓴다 (제목만 "기본 추천 코스").
- `ai.provider=http`: `HttpAiCourseClient` — `POST {AI_BASE_URL}/v1/courses`, `Authorization: Bearer {AI_API_KEY}`, 응답 대기 20초. 시간 초과는 `AiTimeoutException`, 그 밖은 `AiCourseException`; 둘 다 작업이 기본 코스로 대신한다. `AiProperties`의 compact constructor가 "http인데 주소 없음"을 서버 시작 때 막는다.
- 요청 계약(`AiCourseRequest`)은 계획 §2 D5 그대로에 `conditions.origin {lat, lng}`만 더했다 (가까운 곳부터 고르려면 출발지가 필요하다).

### 5. 결과·다시 추천·저장
- `GET /api/recommendations/{id}`: 상태마다 모양이 달라서 `RecommendationStatusResponse`를 sealed interface + record 3개(Pending/Result/Failed)로 나눴다. 남의 요청·만료·Redis 결과 없음은 모두 404 (존재 여부를 알려주지 않는다).
- 타임라인 칸은 `CourseResponse.TimelineItem` sealed interface + `@JsonTypeInfo(property="type")`. JSON에 `type: place|move|meal`이 붙고, Redis에서 다시 읽을 때도 같은 타입으로 돌아온다. move에는 저장 때 일정 항목으로 옮기려고 `distanceMeters`를 같이 둔다.
- `POST …/retry`: 직전 조건 그대로 새 요청(`AI_RETRY`, `previous_request_id`)을 만들고 1회 쓴다. 빼달라고 한 곳과 직전 코스의 장소는 −0.5.
- `POST …/save` (`RecommendationSaveService`, 한 트랜잭션): Redis의 코스를 D4 `PlanDraft`로 바꾼다. 고른 식사 칸은 그 시각의 음식점 항목이 되고, 고르지 않은 식사 칸과 사용자가 뺀 장소는 저장하지 않는다. 이동은 결과의 값을 쓰되 **앞 항목이 바뀐 항목만**(식사 뒤, 뺀 장소 뒤) `RouteService.routes`로 다시 계산한다. `{tripId}` → `TripService.addPlan(makeConfirmed)`, `{newTrip}` → `createTripWithPlan` (제목 "서울 1박 2일"/"서울 당일치기", 기간·동행·지역(시·군·구 1~5개면 그것, 아니면 시·도)·출발지를 추천 조건으로 채움). 뺀 장소는 `BehaviorSignalEvent(AI_REMOVE)`; SCHEDULE_SAVE 신호는 D4가 보낸다. D4에서 403/422가 나면 아무것도 남지 않는다.

### 6. 정리 배치·탈퇴
- `RecommendationCleanupJob` (매시 30분): 10분 넘은 PENDING → FAILED(`INTERNAL`) (작업 중 서버가 꺼진 경우, FE가 영원히 기다리지 않게). 24시간 지난 요청의 출발지 좌표·주소 삭제.
- `RecommendationWithdrawListener` (동기 `@EventListener`, 탈퇴와 같은 트랜잭션): 자식 → 요청 순서로 JPQL DELETE, 그리고 Redis 결과·진행 키 삭제. 엔티티를 불러와 `remove`하지 않는 이유는 D4와 같다 (영속성 컨텍스트에 남은 엔티티가 지운 회원을 가리키면 회원 삭제가 실패한다).

- **`CourseRouter` 포트를 만들지 않았다.** 계획의 phase A/B 구분이 없어져서(§1 FINAL) D4 `RouteService`를 바로 쓴다. 어댑터와 `MoveLeg` record를 두면 같은 값을 한 번 더 옮겨 담기만 한다.

- `RECOMMEND_RETRY` 응답도 `warnings: []` 필드를 가진다 (요청과 같은 record).
- `ContentNearbyService.countWithin(type, lat, lng, radius)` 추가 (D1 파일, 메서드 하나). 기존 `nearby`는 0건이면 반경을 두 배로 넓혀서 "1km 안 음식점 수"로 쓸 수 없다.
- `recommendation.pending-timeout`(10m)·`origin-retention`(24h)·`cleanup-cron`을 설정으로 뺐다.
