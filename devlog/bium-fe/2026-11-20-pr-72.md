## 요약
- 공유 냉장고에서 내보내지거나 초기 목록 로딩에 실패한 후 화면에서 '다시 시도' 시 상단 헤더와 냉장고 상태가 정상 복구되도록 공통 로직을 개편했습니다.
- API 응답 중 `FRIDGE_NOT_FOUND` 감지 시 캐시된 냉장고 목록을 만료 처리하고, 다시 요청하여 유효하지 않은 냉장고 선택을 해제하도록 구현했습니다.
- 개별 화면을 각각 수정하는 대신 `fridgeStore`, `getMyFridge()`, `client.ts` 등 공통 레이어 중심 수정으로 동시 요청 및 race condition 문제를 해결했습니다.

## 변경 내용
- **목록 수신 실패 복구 및 헤더 동기화**: `getMyFridge()`가 스토어의 `getFridges()`를 거치도록 변경하여 헤더와 화면이 동일한 요청을 공유하게 하고 중복 요청을 방지했습니다.
- **내보내진 후 캐시 만료 처리**: API 클라이언트(`client.ts`)에서 `FRIDGE_NOT_FOUND` 오류 감지 시 기존 저장된 목록을 old 상태로 변경하여 다음 요청 시 최신 목록을 받아오도록 수정했습니다.
- **선택된 냉장고 무효화**: 새로 받은 냉장고 목록에 기존 선택된 냉장고가 없으면 선택 상태를 비우고 화면을 다시 불러오도록 로직을 추가했습니다.
- **임박 재료 다시 불러오기 연동**: `UrgentIngredientList.tsx`에서 '다시 불러오기' 실행 중 `FRIDGE_NOT_FOUND` 에러 발생 시 냉장고 목록부터 다시 갱신하도록 처리했습니다.
- **늦은 요청 응답 덮어쓰기 방지**: `addFridge()` 호출 시에도 요청 번호를 올려, 참여 전에 보낸 이전 목록 응답이 늦게 와서 방금 참여한 냉장고를 지우지 않도록 처리했습니다.

## 의도
- 공유 냉장고에서 내보내진 사용자가 내 냉장고, AI 레시피, 도감 등에서 '다시 시도'를 눌러도 이전 목록 캐시 때문에 지속해서 404 오류가 발생하는 현상을 막기 위함입니다.
- 앱 진입 시 냉장고 목록 조회가 실패하여 헤더의 냉장고 버튼이 안 보이게 된 경우, 화면 내 재시도 동작만으로 헤더 버튼까지 함께 복구되도록 UX를 개선하려 했습니다.

## 트러블 슈팅
- 냉장고 참여 요청 전 보냈던 목록 조회 응답이 뒤늦게 도착하여 방금 추가된 냉장고를 지워버리는 문제 → `addFridge()` 호출 시에도 요청 번호(version)를 증가시켜 이전 요청의 늦은 응답을 버리도록 해결.
- `FRIDGE_NOT_FOUND` 발생 후 재시도를 해도 헤더가 이전 데이터를 갖고 있어 404 에러가 반복되는 문제 → `client.ts` 수준에서 해당 에러 감지 시 스토어 캐시를 만료시키고, 스토어 갱신 시 존재하지 않는 냉장고 선택 상태를 비우도록 해결.

## 생각 정리
- `client.ts`와 `fridgeStore.ts` 사이에 발생할 수 있는 순환 참조(circular import) 가능성을 완전히 제거하려면 에러 이벤트를 어떤 방식으로 분리하는 것이 좋을까?
- 네트워크 레이스 조건을 해결하기 위해 도입한 요청 번호(request counter) 방식 대신, `AbortController`나 데이터 패칭 라이브러리의 취소 기능을 활용하는 기법은 어떻게 적용할 수 있을까?
- 복잡한 비동기 에러 복구 시나리오를 다루면서 Mock 스크립트 기반 테스트의 유용성을 체감했는데, 앞으로 이를 표준 단위 테스트로 어떻게 발전시킬 수 있을까?
