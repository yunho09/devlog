## 요약
레시피 상세 페이지에서 요리 완료 또는 되돌리기를 실행했을 때 냉장고 재료 보유 표시가 최신 상태로 갱신되지 않던 이슈를 해결했습니다. 백엔드의 레시피 상세 응답 내 보유 정보가 생성 시점 데이터로 고정되어 있던 문제를 보완하고자 `GET /api/recipes/{id}/cooking-candidates` API를 활용해 현재 냉장고 재료 상태를 재조회하도록 변경했습니다. 또한 비동기 갱신 과정에서 로딩 UI 노출 없이 기존 UI를 유지하며, 비동기 응답 순서 꼬임을 방지하는 처리를 적용했습니다.

## 변경 내용
- `RecipeDetailPage` 페이지 진입 시 및 요리 완료/되돌리기 성공 직후 `GET /api/recipes/{id}/cooking-candidates` 호출 추가
- `source`가 `FRIDGE`인 재료 중 후보(candidates)가 없는 경우 "냉장고 보유" 표시 제거 및 "냉장고 매칭" 항목에서 제외 처리
- 재조회 중 로딩 상태 표시 없이 기존 UI 상태를 유지하다 응답 완료 시 일괄 업데이트
- 요청 번호 추적을 적용하여 느리게 도착한 이전 응답이 최신 상태 응답을 덮어쓰지 않도록 방지
- 재조회 실패 시 기본 레시피의 `source` 표시로 안전하게 폴백

## 의도
요리 완료 후 재료가 차감되어도 레시피 상세의 `GET /api/recipes/{id}` 응답 내 `source`와 `fridgeMatches` 값이 생성 시점 기준으로 고정되어 있어 실시간 반영이 되지 않았습니다. 백엔드 데이터 한계를 보완하기 위해 실시간 냉장고 상태를 알 수 있는 `cooking-candidates` API를 재료 이름 기준으로 짝지어 클라이언트에서 "냉장고 보유" 상태를 맞추도록 구현했습니다.

## 트러블 슈팅
- 요리 완료 후에도 `GET /api/recipes/{id}`의 보유 재료 정보가 고정되어 표시가 바뀌지 않는 문제 → `GET /api/recipes/{id}/cooking-candidates` API를 호출해 재료 이름 단위로 실시간 냉장고 보유 여부를 비교하여 UI를 갱신하도록 해결했습니다.
- 요리 완료와 되돌리기를 연속 실행할 경우 늦게 들어온 비동기 응답이 최신 UI 상태를 덮어쓸 가능성 → 요청 번호를 추적하여 마지막에 요청한 응답만 상태에 반영하도록 처리해 race condition을 방지했습니다.
