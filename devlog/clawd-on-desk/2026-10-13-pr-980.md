- PR 본문: ## Summary / 摘要

Closes #979.

On Linux the pet disappeared as soon as the user switched workspace, and only came back on returning. On macOS it follows the user across Spaces. With this PR, the pet stays on every workspace on X11/XWayland. The render window never takes keyboard focus from the app the user is working in.

Root cause: the only pet-window call to `setVisibleOnAllWorkspaces()` is in `reapplyMacVisibility()` (`src/topmost-runtime.js`), which returns immediately off macOS. Nothing else pins the pet windows on Linux.

## What changed / 变更内容

**The pet follows workspaces on Linux**

- `applyLinuxAllWorkspaces()` in `src/pet-window-runtime.js` calls `setVisibleOnAllWorkspaces(true)` on the render window and the hit window. On X11 this sets `_NET_WM_STATE_STICKY`.
- It runs before each window's first `showInactive()`, with no macOS-only options, wrapped in `try`.
- In `createHitWindow()` it sits after main's Windows `prepareActivation()` setup and its fallback.

**The render window stays out of WM keyboard focus on X11**

- **Why:** a sticky window that can take focus wins mutter's default focus on every workspace switch. mutter treats a window without `WM_HINTS` as focusable, and `meta_window_make_most_recent()` moves a sticky window to the front of every workspace's MRU list. Review found that switching workspaces 1 → 2 → 1 left focus on the pet.
- **Fix:** the render window is output-only, since input goes through the hit window. A new module, `src/linux-x11-input-hint.js`, writes ICCCM `WM_HINTS { InputHint, input: False }` on it over a private XCB connection, using Koffi. `main.js` injects it into `createRenderWindow({ applyNoInputHint })`, which applies it right after construction. mutter re-reads the hint, so it covers every later focus decision.
- **Gating:** enabled only when Chromium resolved the X11 Ozone backend. It is best-effort, and a no-op on Windows, macOS, native Wayland, or when libxcb or Koffi is missing.
- **Why not Electron's own option:** `focusable: false` makes Chromium create an override-redirect window, which would change stacking and placement.
- **Contract recorded:** one line under High-Risk Gotchas in `AGENTS.md`.

**Tests**

- `test/pet-window-runtime.test.js` has a `cross-workspace visibility (#979)` block with mutually exclusive platform fixtures. It covers:
  - the sticky call on Linux only, before `showInactive()`
  - macOS still delegating to `reapplyMacVisibility()`
  - missing and throwing native methods
  - the no-input hint: applied on Linux during creation, ahead of `showInactive()`; never on Windows or macOS; and a throwing hint not breaking window creation
- `test/linux-x11-input-hint.test.js` covers:
  - the exact `WM_HINTS` write
  - XID decoding
  - the X11 gate
  - load, connection and request failures, plus cleanup
  - the `main.js` wiring
  - on Linux only, the real libxcb bindings: Koffi prototypes against the C signatures, and the by-value cookie through `xcb_change_property_checked` and `xcb_request_check` on an error connection

## Scope control / 范围控制

**Unchanged:**

- the constructor's focusability and window type
- `focusable: !isLinux` on the hit window (the AGENTS.md drag contract)
- main's Windows activation work
- the macOS `reapplyMacVisibility()` path

**Deliberately not done:**

- Bubbles and the HUD are not pinned to all workspaces.
- Nothing is re-applied at later lifecycle points. Hide/show and restart were checked to keep both the sticky state and the hint.
- Startup focus is not addressed. Chromium maps the render window inside the constructor, so mutter can focus it once at startup, before the hint lands. `main` does the same, and the focus ends at the next click or workspace switch. Creating it with `show: false` on Linux would close that and is offered as a follow-up.
