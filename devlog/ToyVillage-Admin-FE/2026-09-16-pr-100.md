# 2026-09-16

## 요약
첨부파일 다운로드 방식을 파일 서버의 원본 파일을 활용해 원래 파일명으로 안전하게 내려받도록 개편했습니다. 공지사항, 업무, 업무보고, 자료실 등 전체 시스템의 상세 및 수정 화면에 이를 일괄 적용했습니다. 외부 CDN 요청 시 보안 유출 및 세션 만료 오동작을 피하기 위해 기존 axios 대신 fetch를 사용한 독립 다운로드 로직을 구현하고 관련 e2e 테스트를 추가했습니다.

## 변경 내용
- **원본 파일 다운로드 구현**: `fileKey`를 파일 서버 주소(`VITE_FILE_BASE_URL`) 뒤에 조합하여 실제 원본 파일을 불러오고, 사용자가 업로드했던 원래 파일명으로 다운로드되도록 개선했습니다.
- **공통 Axios 대신 Fetch 적용**: 외부 파일 서버(CDN) 호출 시 공통 axios를 거치면 인증 토큰이 외부로 노출되거나, 403 응답 발생 시 로그인 세션 만료로 오인해 튕기는 문제를 예방하고자 네이티브 `fetch`를 사용한 다운로드 로직을 수립했습니다.
- **다양한 작업 화면 연동**: 업무 상세, 업무보고 상세, 업무 수정, 자료실 업로드 필드, 공지사항 등록 및 상세 등 시스템 내 첨부파일 다운로드가 필요한 전체 UI 영역에 새 방식을 연동했습니다.
- **오류 피드백 및 복구**: 다운로드 실패 시 사용자에게 오류 알림을 표시하고, 사용자가 재시도하여 다운로드에 성공할 경우 실패 알림이 화면에서 자동으로 사라지도록 처리했습니다.
- **테스트 코드 추가**: 첨부파일 다운로드 성공 및 실패 케이스를 검증하는 Playwright e2e 테스트(`.spec.ts`)를 신설했습니다.

## 의도

## 트러블 슈팅
- **외부 CDN 요청 시 공통 Axios의 인증 토큰 노출 및 세션 만료 처리 오동작**
  - **문제**: 파일 서버(CDN)에 요청을 보낼 때 공통 axios 인스턴스를 사용하면 헤더에 담긴 JWT 토큰이 타사 CDN 환경으로 불필요하게 전송되는 보안 취약점이 있었습니다. 또한, CDN에서 403 에러가 반환될 경우 axios 공통 인터셉터가 이를 애플리케이션 세션 만료로 판단해 사용자를 강제로 로그아웃시키는 버그가 우려되었습니다.
  - **해결**: 토큰 헤더가 자동으로 포함되지 않으며 외부 인터셉터가 개입할 수 없는 브라우저 표준 `fetch` API를 별도로 분리 구현하여 안전하게 다운로드 요청을 전송하도록 조치했습니다.
- **다운로드 재시도 성공 시 잔존하는 에러 메시지**
  - **문제**: 다운로드 중 일시적인 실패로 인해 에러 경고 문구가 발생한 이후, 사용자가 재시도하여 다운로드에 최종 성공했음에도 화면 상의 실패 알림 UI가 지워지지 않고 남아 있었습니다.
  - **해결**: 다운로드 로직이 최종 성공으로 분기될 때 에러 메시지 상태를 초기화하는 제어 코드(`c3ec05b`)를 탑재하여 UI 상태 정합성을 보장했습니다.

## 생각 정리
1. 파일 다운로드 요청 시 Axios 인터셉터가 주입하는 JWT 토큰이 외부 CDN으로 노출되지 않도록 전용 `fetch` 함수를 도입했는데, 이 외에도 외부 외부 API 호출 시 토큰 노출을 방지하기 위한 안전한 아키텍처는 무엇일까?
2. 다운로드 실패 및 재시도 성공 상황에 맞추어 에러 상태를 화면에서 깔끔하게 핸들링하고 UI를 초기화하는 일련의 상태 관리 전략을 어떤 컴포넌트 패턴으로 더 추상화할 수 있을까?
3. 브라우저 API 환경(Blob, fetch 등)과 파일 서버 사양에 맞춰 다운로드 로직을 구현하면서, 웹 표준 명세를 깊이 이해하고 프론트엔드 보안적 요소를 함께 고려하는 것의 중요성에 대해 무엇을 느꼈는가?
