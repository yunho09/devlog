## 요약
에러 모니터링 과정에서 유실되고 있었던 일부 API 오류와 쿼리·뮤테이션 실패 항목을 Sentry에 전송하도록 수집 환경을 개선했습니다. 200 응답 내부의 형식 검증 실패, API 400 에러, 세션 강제 종료 시의 상세 사유 등을 Sentry 로그 및 경고로 기록합니다. 변경된 리포팅 흐름과 세션 종료 로직의 신뢰성을 검증하기 위해 Playwright 기반의 E2E 테스트 코드 및 모킹 설정을 함께 구축했습니다.

## 변경 내용
- **에러 수집 영역 확장**: 응답 데이터의 스키마 검증 실패와 같은 쿼리·뮤테이션 요청 함수 내부 실패 사례를 Sentry로 전송하도록 글로벌 `queryClient` 설정을 보완했습니다.
- **특정 에러 필터링 및 400 에러 수집**: API 400 에러를 5xx 에러처럼 모니터링 대상으로 추가하는 한편, 요청 취소(Cancel)나 비즈니스 로직상 대응할 수 있는 무해한 4xx 오류 등은 보고 대상에서 제외했습니다.
- **강제 로그아웃 원인 추적**: 토큰 저장소 미존재, 토큰 재발급 거부, 재발급 후에도 403 에러 발생 등 구체적인 세션 종료 사유를 Sentry Warning 레벨로 기록하는 로직을 통합했습니다.
- **E2E 테스트 도입**: Sentry 통신을 에뮬레이트하는 모의 서버(`sentry-server.ts`)와 에러 전송 흐름을 통합 테스트하는 E2E 코드(`sentry.spec.ts`)를 추가했습니다.

## 의도
네트워크 상으로는 200 응답이나 일부 4xx 응답으로 기록되지만 실제 클라이언트 로직 내부에서 유효성 검사 실패나 예기치 못한 세션 만료 등의 오류가 숨겨지는 현상을 추적하기 위함입니다. 이를 통해 운영 상의 잠재적인 에러를 조기에 명확히 인지하고 디버깅 효율성을 극대화하고자 한 의도로 판단됩니다.
