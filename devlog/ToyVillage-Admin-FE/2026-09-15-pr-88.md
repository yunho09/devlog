# 2026-09-15

## 요약
이 PR은 ToyVillage-Admin-FE 프로젝트의 개체관리 도메인에 필요한 UI 퍼블리싱 작업을 완료하고 테스트 사양을 구축하기 위해 진행되었습니다. 종, 개체, 관찰 내역의 목록·상세·등록·수정 화면을 추가하고, 이를 지원하는 다수의 공용 및 도메인 특화 컴포넌트를 설계했습니다. Mock 데이터를 기반으로 승인 시나리오 및 e2e 테스트 사양을 마련하여, API 개발 전 화면의 신뢰성을 선제적으로 검증할 수 있도록 조치했습니다.

## 변경 내용
- **개체관리 화면 및 라우팅 추가**: 종 목록/상세, 종 등록/수정, 개체 등록/수정/상세, 관찰 상세/수정 등의 9개 페이지 구현 및 `src/app/App.tsx`에 라우팅 등록.
- **도메인 엔티티 모델 및 Mock 구축**: 종(Species), 개체(Individual), 관찰(Observation) 엔티티의 데이터 모델 정의 및 관련 Mock 데이터 배치.
- **공용 UI 컴포넌트 강화 및 신규 추가**: 
  - 사진 업로드 필드(`PhotoUploadField`)와 드롭존(`FileDropZone`) 분리.
  - 삭제 모달 설명 및 초점 프레임 Hook 추가, 케밥 메뉴의 배치 옵션과 초점 복귀 보강.
  - 첨부 칩(`AttachmentChip`), 폼 필드 카드 및 라벨, 법정지정분류 뱃지, 성별 뱃지, 분류군 탭바 설계.
- **테스트 명세서 및 시나리오**: 각 페이지의 UI 명세(spec.md)와 기능 검증을 위한 승인 시나리오(scenario-draft.md, approved.json) 추가.
- **연결 보류 처리**: 대상 ID와 이동 목적지가 아직 확정되지 않은 `관찰 및 특이사항 보러가기` 및 `먹이 급여 기록 확인하기` 링크는 임시 비활성화 유지.

## 의도
ToyVillage 서비스 내 핵심이 되는 동물 및 개체, 관찰 일지 관리 도메인의 어드민 UI 레이아웃과 데이터 흐름을 사전에 명확히 하고자 했습니다. 백엔드 API 명세가 완전히 연동되기 전에도 승인 시나리오와 Mock 기반 e2e 테스트를 통과하도록 구성함으로써, 화면 기능의 완성도를 독립적으로 증명하고 추후 통합 개발의 리스크를 낮추기 위함입니다.

## 변경 파일
- `src/app/App.tsx`: 종 및 개체, 관찰 상세와 수정 관련 대량의 신규 라우트 배치.
- `src/entities/` (individual, observation, species): 종, 개체, 관찰의 타입 선언, Mock 생성기 및 테이블 표 뷰 등의 도메인 핵심 엔티티 구성요소 추가.
- `src/features/` (individual-form, observation-form, species-form): Zod 검증 기반의 도메인 특화 폼 비즈니스 로직과 레이아웃 컴포넌트 추가.
- `src/pages/species/`: 개체관리 목록 및 세부 페이지, 생성/수정용 FormPageLayout 정의.
- `src/shared/ui/`: `FileDropZone`, `PhotoUploadField`, `AttachmentChip` 등 공용 레이아웃 요소 신설 및 기존 `KebabMenu`, `DataTable` 기능 보강.
- `harness/publishing/`: UI 동작 검증을 보장하기 위한 다량의 spec 마크다운 및 시나리오 결과 JSON 파일 생성.

## 트러블 슈팅
- **develop 브랜치와의 병합 충돌** → 기존 사이드바 아코디언 메뉴 구조의 흐름을 방해하지 않고 `개체관리 > 개체 카드` 아래에 종 목록(`/species`) 메뉴를 자연스럽게 포함하도록 조율했습니다.
- **SectionHeader 충돌 우려** → 기존 먹이 급여 상세 화면에서 사용 중이던 `SectionHeader` 컴포넌트의 기존 로직을 안전하게 보전하기 위해, 코드를 전면 수정하는 대신 필수적인 `unit`과 `action` 프로퍼티(슬롯)를 하위 호환성을 갖추는 방식으로만 추가하여 해결했습니다.
- **ID 불일치로 인한 이동 오류 위험** → 아직 연결 대상 ID와 구체적인 이동 경로가 확정되지 않은 `관찰 및 특이사항 보러가기` 및 `먹이 급여 기록 확인하기` 기능은 불필요한 오류를 미연에 방지하기 위해 임시 비활성 상태로 처리해 머지했습니다.

## 생각 정리
1. Mock 기반의 승인 시나리오 테스트(spec)를 개발 초기 단계에서 이처럼 촘촘히 작성했을 때, 이후 실 연동 API가 구현되면서 발생할 마이그레이션 작업을 어떻게 효율화할 수 있을까요?
2. `SectionHeader` 리팩터링 사례처럼 공용 컴포넌트의 하위 호환성을 해치지 않으면서 새로운 도메인 기능의 요구사항을 반영하기 위해, 우리는 평소에 컴포넌트를 어떤 구조로 열어두어야 할까요?
3. 100개가 넘는 신규 화면 파일 및 시나리오 파일을 생성하는 과정에서, 구조적 일관성을 지키기 위해 어떠한 설계 표준을 고민했는지 회고해 보면 좋겠습니다.
