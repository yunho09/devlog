# 2026-09-29

## 요약
어플리케이션의 에러 모니터링 및 성능 추적을 위해 Sentry를 성공적으로 도입했습니다. API 에러 중 사용자 인증 만료 등의 4xx 계열을 제외한 5xx 에러, 네트워크 장애, 타임아웃 발생 시에만 선택적으로 Sentry에 전송하도록 필터링했습니다. 또한 빌드 시 소스맵을 Sentry에 업로드한 뒤 배포 디렉터리(`dist`)에서는 제거하도록 구성하여 코드 보안과 실시간 디버깅 편의성을 동시에 확보했습니다.

## 변경 내용
- **Sentry 라이브러리 및 소스맵 업로드 도구 도입**: Sentry 연동을 위한 패키지를 추가하고, `VITE_SENTRY_DSN` 환경 변수가 설정되어 있을 때만 동작하도록 비활성화 처리를 지원합니다.
- **필터링된 API 에러 수집**: 401, 403 등 토큰 재발급과 관련된 일반적인 흐름의 4xx 에러를 제외하고, 5xx 서버 에러, 네트워크 에러, 타임아웃 에러만 Sentry로 수집하도록 가공했습니다.
- **글로벌 에러 경계(RouteErrorPage) 적용**: React Router 최상위에 `errorElement`로 작동하는 `RouteErrorPage`를 추가하여, 렌더링 도중 발생한 에러를 감지 및 로깅하고 사용자에게는 새로고침 안내 화면을 제공합니다.
- **성능 측정 전송**: 페이지 로드 속도, API 응답 속도 및 Web Vitals 데이터를 100% 비율로 수집하도록 성능 추적 샘플링 설정을 추가했습니다.
- **소스맵 보안 처리**: `vite.config.ts` 설정을 변경하여 빌드 단계에서 소스맵을 Sentry에 업로드한 후, 실제 사용자에게 서빙되는 빌드본에서는 `.map` 파일을 완전히 삭제하도록 구성했습니다.

## 의도
운영 및 스테이징 환경에서 예기치 못하게 발생하는 런타임 오류와 서버 장애를 즉각적으로 인지하고 원인을 파악하기 위함입니다. 특히 무분별하게 유입될 수 있는 4xx 클라이언트 에러를 걸러내어 Sentry 할당량 낭비를 방지하고, 소스맵 노출 없이 프론트엔드의 원래 에러 라인을 정확히 추적할 수 있도록 보안과 디버깅 생산성을 조율했습니다.

## 생각 정리
1. API 에러 중 토큰 만료 등의 4xx 계열은 의도적으로 수집 대상에서 제외했는데, 추후 모니터링 과정에서 사용자 액션 분석이나 특정 인가 이슈 추적을 위해 일부 4xx 에러의 수집 필요성이 대두된다면 필터링 기준을 어떻게 개선할 수 있을까요?
2. 성능 추적 샘플링 비율을 100%로 설정한 현재 상태에서 트래픽이 크게 늘어날 경우, 비용 제어나 API 호출량 할당 한계에 도달하지 않도록 점진적으로 샘플링 비율을 낮추는 기준을 어떻게 설계해야 할까요?
3. 에러 로깅 라이브러리를 직접 프로젝트에 연동하고 예외 처리 범위를 좁혀 나가는 과정에서 개발자로서 어떤 점을 고려해야 하는지 무엇을 느끼셨나요?
