# 2026-10-01

## 요약
실제 배포 환경의 점검 과정에서 발견된 프론트엔드 이슈 3건을 신속하게 해결한 PR입니다. 경력 수정 시 백엔드 API 계약에 맞춰 본문 데이터 포맷을 가공하여 400 에러를 수정했고, 누락되던 유효성 검증 실패 사유를 분석하여 상세 안내 메시지가 화면에 노출되도록 개선했습니다. 또한, 문서 미리보기 영역 아래쪽에 숨겨져 보이지 않던 발급 실패 에러 안내 메시지를 사용자 뷰포트 영역 내부로 조절하고 스크롤 포커스를 추가했습니다.

## 변경 내용
- **경력 수정 요청 데이터 규격 조율**:
  - 성별 필드 전송 값을 `"M"`/`"F"`에서 백엔드 Enum 명칭인 `"MALE"`/`"FEMALE"`으로 변환하여 전송하도록 수정했습니다. (성별 미지정 시에는 요청을 차단하고 경고를 띄움)
  - 구분(`division`) 및 근무 형태(`employmentType`) 필드가 비어있을 때 빈 문자열(`""`) 대신 `null`을 넘겨 백엔드 `@AssertTrue` 검증을 통과하도록 변경했습니다.
  - 임용일, 퇴사일, 만료일 등 날짜 필드의 빈 값(`""`, `"-00-00"`) 또한 `null`로 치환하여 `LocalDate` 역직렬화 실패 현상을 예방했습니다.
  - `UpdateCertificateRequest` 타입을 수정하여 빈 문자열 대신 `string | null` 타입을 사용하도록 정립했습니다.
- **검증 에러 상세 사유 매핑 로직 구축**:
  - 백엔드 검증 실패 시 내려오는 `ValidationErrorResponse` 내부의 `error` 맵 정보를 파싱하여 `ApiError.fieldErrors` 객체로 추출하도록 로직을 변경했습니다.
  - 구체적인 상세 에러 문구를 상위에 띄울 수 있게 에러 메시지 우선순위를 재설정했습니다. (`code` 매핑 -> `error` 맵 -> `status` 매핑 -> `message` -> 기본값)
  - 순서가 들쭉날쭉할 수 있는 `HashMap` 에러 응답 특성을 고려해, 에러 메시지를 필드명 기준으로 사전 정렬하여 결합하도록 개선했습니다.
- **에러 메시지 레이아웃 및 스크롤 개선**:
  - `CertificatePreviewView` 컴포넌트 내부에서 발생하는 제출 에러 UI 영역을 긴 세로 스크롤을 유발하는 문서 뷰어 상단(파일명 표시 영역 아래)으로 이동시켰습니다.
  - 에러가 발생하면 사용자가 바로 인지할 수 있도록 에러 메시지 영역으로 자동 스크롤(`scrollIntoView`)되게끔 조치했습니다.
- **검증 테스트 작성**:
  - `api.test.ts`, `certificates.test.ts`, `CertificatePreviewView.test.tsx` 파일을 생성 및 보완하여 신규 구현된 에러 우선순위 정렬, 바디 포맷 변환 로직 및 컴포넌트 렌더링 상태를 테스트했습니다.

## 의도
배포 점검 도중 실사용자 관점에서 완전히 차단되어 있던 기능 정상화 및 UX 품질 개선을 위한 작업입니다. 백엔드 도메인 성격에 따라 다르게 설정되어 있던 Enum 표기 체계나 필드 제약 조건을 프론트엔드 전송 단계에서 안전하게 마스킹 및 전처리하여 API 불일치 오류를 사전에 차단하고자 했습니다. 또한 에러가 발생하더라도 구체적인 실패 원인을 상위 레이아웃에 직접 표시하고 자동 포커싱을 지원하여 사용자가 피드백을 직관적으로 수용하고 바로 대응할 수 있도록 도왔습니다.

## 트러블 슈팅
- **경력 수정 저장 시 무조건 400 에러 발생 → 데이터 규격 및 타입 전처리**
  - 문제: 경력 사항을 수정하려 할 때, 백엔드 엔드포인트의 특화 Enum 구조 및 어설션 검증 방식(성별 표기 `"M"/"F"`, 빈 문자열 포맷 허용 안 됨 등)과 어긋나 요청이 항상 반려되었습니다.
  - 해결: 성별 값을 `"MALE"/"FEMALE"` 형태로 변경하고, 비어 있는 구분, 근무형태, 날짜 문자열들은 명시적인 `null` 값으로 역변환하여 백엔드가 적절하게 역직렬화하고 검증할 수 있도록 수정했습니다.
- **백엔드 입력값 검증 실패 시 단순히 "서버 장애" 문구만 나오는 현상 → 에러 파싱 계층 개선**
  - 문제: 백엔드의 검증 오류 형식은 개별 `error` 맵 안에 디테일한 에러 메시지들이 들어있으나, 기존 프론트엔드 에러 가공 로직(`parseErrorBody`)이 이를 유실하여 범용 에러 문구 혹은 500 장애 문구로 덮어쓰던 이슈가 있었습니다.
  - 해결: 응답의 `error` 맵을 읽어내 `ApiError.fieldErrors`에 담은 후, 매핑된 상세 필드 에러들을 필드명 알파벳 순서대로 정렬하여 화면에 정확하게 뿌려주도록 매핑 우선순위를 재설계했습니다.
- **권한 부족 등 발급 실패 메시지가 발생해도 사용자는 멈춘 것처럼 느낌 → 뷰포트 배치 변경 및 스크롤 강제 적용**
  - 문제: 발급에 실패했을 때 나타나는 에러 배너가 긴 프리뷰 문서 뒤인 약 1875px 하단 영역에 노출되고 있어서 상단 완료 버튼을 누른 민원인은 메시지를 전혀 인지하지 못하는 상태였습니다.
  - 해결: 에러 안내 요소를 문서 프리뷰 위(파일명 바 바로 밑)로 재배치하고, 오류 감지 즉시 `scrollIntoView` API를 이용해 화면을 강제로 에러 메시지 방향으로 이동시켜 경고를 명확히 노출했습니다.

3. 이번 배포 환경 점검 과정에서 발견된 스크롤 밖 에러 노출 버그처럼 실제 기기 규격이나 뷰포트 크기에 종속적인 사용자 경험 오류를 사전 로컬 개발 과정에서 효과적으로 포착하고 검증할 방안은 무엇일까요?
