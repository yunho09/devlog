# 2026-10-06

## 요약
경력증명서 발급 및 경력사항 등록 과정에서 발견된 프론트엔드 레이스 컨디션과 개인정보 노출 결함 등을 전면 수정하였습니다. 백엔드 실서버 API와 계약을 확정하고 서버 PDF 미리보기, 민원인 선택 발급, 경력 10건 제한 등의 기능을 연동하였습니다. 아울러 페이지네이션 기준 정렬, 에러 코드 기반의 권한 처리, 토큰 재발급 흐름을 개선하고 비밀번호 변경 화면을 추가하였습니다.

## 변경 내용
- **발급 및 등록 플로우 결함 수정**:
  - 경력 조회 로딩 도중 다른 대상자로 변경할 때 오작동하는 레이스 컨디션을 막기 위해 요청 ID 가드, 조회 버튼/라디오 버튼 비활성화, 응답 검증 단계를 추가하였습니다.
  - "추가 발급하기" 클릭 시 공용 PC에 개인정보가 남지 않도록 이전 대상자 정보를 초기화하였습니다.
  - 재직 중인 경력의 종료일 표기를 "현재"로 통일하고, 민원인 PDF 파일명 등에 로그인 ID가 아닌 실명이 나오도록 수정하였습니다.
- **백엔드 API 신규 연동**:
  - `/api/certificates/preview`를 연동하여 서버 PDF를 iframe 미리보기로 출력하며, 실패 시 기존 마크업 렌더로 폴백되게 하였습니다.
  - 민원인 본인 선택 발급(`GET /api/certificates/self`) 및 한 화면당 경력 최대 10건 제한 정책을 적용하였습니다.
- **페이지네이션 및 다중 공통 처리**:
  - 백엔드의 1-based 페이지 변경 사항을 전사 반영하고, `Pagination` 컴포넌트를 공용으로 추출하였습니다.
  - 검색 결과가 빈 페이지일 때 단순히 "중복 없음"으로 오판하지 않고 마지막 유효 페이지를 재조회하도록 처리하였습니다.
- **에러 및 세션 처리 고도화**:
  - 백엔드 예외 코드를 기반으로 401, 403, 409 등을 판정하도록 유연화하였습니다.
  - 리프레시 토큰을 활용한 새 토큰 재발급(`reissue`) 및 세션 연장 기능을 연결하고, 동시 요청 시 401 처리가 겹쳐 쿼리 파라미터가 중첩되는 현상을 해결하였습니다.
- **기타 편의성 개선**:
  - 필수 입력 필드에 별표 표시를 달고 진행 버튼 비활성화 시 구체적인 미입력 사유를 사용자에게 안내하는 문구를 제공합니다.
  - 공통 비밀번호 변경 페이지(`/password/change`)를 추가하고 초기 비밀번호 여부를 판단하여 분기하도록 개선하였습니다.

## 의도
백엔드 실서버 배포 스펙 및 QA 피드백에 맞춰 프론트엔드가 가진 흐름상의 오동작(레이스 컨디션, 잘못된 초기화, 공용 PC 보안 위협)을 해결하고, 명세와 달랐던 실제 계약 조건들을 코드로 직접 검증하여 정합성을 일치시키기 위함입니다.

## 트러블 슈팅
- **대상자 변경 시 이전 데이터가 남는 레이스 컨디션**: 경력 로딩 중에 다른 대상자를 선택하면 이전 대상자의 데이터가 발급 요청에 함께 조립되는 현상이 발생했습니다. → 요청 ID 가드를 심고 응답 적용 전에 선택한 대상자 정보와 일치하는지 재확인 단계를 거쳤으며, 로딩 중에는 조회 버튼, 이름 입력창 및 대상자 라디오 버튼 자체를 잠그도록 제어하여 근본적으로 해결했습니다.
- **백엔드 page index 기준 변경(0-based -> 1-based)으로 인한 400 에러**: 백엔드가 검색 page 인덱스를 1부터 받도록 제약을 변경하면서 FE의 0-based 요청이 에러를 일으켰습니다. → FE 전반의 요청/응답을 1부터로 통일하고, 화면단에서 적용하던 `-1` 보정 연산들을 제거하여 싱크를 맞췄습니다.
- **토큰이 만료되었음에도 세션이 풀리지 않아 다른 API가 지속해서 실패하는 문제**: 기존 토큰 만료 여부 판정 로직이 만료 시각만 보고 로그아웃을 처리해 예외를 온전히 잡지 못했습니다. → API 실패 시 백엔드의 에러 `code`(`EXPIRED_TOKEN`, `INVALID_TOKEN` 등)를 기준으로 401을 판정하게 하고 세션 무효화 흐름을 체계화했습니다.
- **외래키를 가진 대상자 삭제 시 백엔드 500 에러**: 연결된 경력이 있는 대상을 API 호출로 지우려 할 때 에러가 발생하거나 데이터 왜곡이 생겼습니다. → 삭제 처리 전에 프론트엔드에서 대상자의 경력 목록을 먼저 검색해 경력이 1건이라도 존재하면 삭제 요청을 차단하고 친절한 안내 팝업을 띄우도록 가드를 추가했습니다.
