# 2026-09-10

## 요약
경력사항 개별 등록 시 발생하는 API 400 에러를 해결하기 위해 프론트엔드 요청 본문을 백엔드 계약 규격에 맞춰 수정했습니다. 근무부서 데이터를 `department` 필드로 전송하고, 입력란이 없는 `division` 및 `employmentType` 필드는 빈 문자열 대신 `null`로 전송하도록 변경했습니다. 또한 불필요한 인적 사항 필드를 제거하고, 백엔드의 404 에러 대응 및 페이지 단위의 예외 처리 로직을 보완했습니다.

## 변경 내용
- **API 요청 모델 수정**: `CreateCertificateRequest` 타입을 변경하여 `department` 필드를 추가하고, `division`/`employmentType` 타입을 `string | null`로 지정했으며, 백엔드에서 받지 않는 `name`, `birthDate`, `gender` 필드를 제거했습니다.
- **데이터 매핑 로직 변경**: `toCreateRequest` 변환기에서 근무부서 입력을 `department` 필드로 매핑하고, 입력란이 없는 `division`과 `employmentType`은 `null`로 매핑하여 전송하도록 수정했습니다.
- **에러 핸들링 보완**: 백엔드에서 반환하는 404(`HUMAN_NOT_FOUND`) 에러 매핑을 추가하고, 미사용되는 409 에러 매핑 및 문구를 제거했습니다.
- **페이지 동작 수정**: 경력 등록이 404 에러로 실패할 경우, 저장되어 있던 `humanId`를 지워 재시도 시 대상자 등록 단계부터 다시 시작할 수 있도록 개선했습니다.
- **배럴 익스포트 보완**: `packages/utils/src/index.ts`에 누락되었던 인증서 관련 유틸 파일의 내보내기를 추가했습니다.
- **테스트 코드 업데이트**: 갱신된 API 계약(null 전송, `department` 키 검증, 인적 사항 미전송, 404 매핑 등)에 맞춰 테스트 코드를 갱신했습니다.

## 의도
백엔드에서 경력사항 등록 API(`POST /api/certificates/create`)를 구현 완료함에 따라, 기존의 405 에러가 사라지고 프론트엔드가 전송하는 데이터 규격이 맞지 않아 발생하던 400 에러를 해결하기 위함입니다. 백엔드의 데이터 유효성 검증 명세에 맞춰 프론트엔드의 DTO와 매핑기(Mapper)를 동기화했습니다.

## 트러블 슈팅
- 문제 → 경력사항 개별 등록 마지막 단계에서 `POST /api/certificates/create` 호출 시, `division` 및 `employmentType` 검증 실패로 인해 `400 Bad Request` 에러가 발생함. 원인은 프론트엔드가 근무부서 값을 `division`에 잘못 매핑하고, 빈 값에 대해 빈 문자열(`""`)을 전송했으나 백엔드는 `null`만을 허용했기 때문임.
- 해결 → `toCreateRequest` 매퍼를 수정하여 근무부서 입력을 `department` 필드로 정상 전달하고, 값이 없는 `division` 및 `employmentType` 필드는 명시적으로 `null`로 지정하여 전송하도록 변경함.
- 문제 → 경력 등록 단계에서 API 요청 실패가 발생했음에도 브라우저 내에 이전 단계에서 생성한 `humanId`가 계속 기억되어 있어, 사용자가 재시도할 때 대상자 생성 과정을 생략하고 바로 경력 등록을 시도해 다시 실패하는 버그가 발생할 우려가 있음.
- 해결 → API 요청이 404 에러로 실패하면 기존 저장된 `humanId`를 즉시 소멸하도록 페이지 상태 관리 로직을 보완하여, 사용자가 대상자 등록 절차부터 안전하게 재시도할 수 있도록 개선함.
