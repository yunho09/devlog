# 2026-09-08

## 요약
대상자 삭제 API(`DELETE /api/human/{humanId}`)를 프론트엔드 화면에 연동하여 잘못 등록된 대상자를 삭제할 수 있는 기능을 추가했습니다. 대상자 조회 결과 표에 삭제 버튼을 노출하고 삭제 처리 중 상태 잠금 및 삭제 후 상태 갱신 로직을 구현했습니다. 백엔드에서 경력 사항 삭제가 연쇄적으로 일어나지 않는 제약 사양을 확인 메시지 내 경고 문구를 통해 사용자에게 사전 고지하도록 보완했습니다.

## 변경 내용
- **대상자 삭제 API 연동**: `packages/utils/src/humans.ts` 파일에 `DELETE /api/human/{humanId}` 요청을 처리하는 `deleteHuman` 유틸리티 함수를 추가하고 에러 코드(401, 403, 404)를 적절한 화면 메시지로 매핑했습니다.
- **삭제 UI 구현**: `CareerEdit` 컴포넌트에 `onDeleteApplicant` prop을 추가하여 해당 prop이 제공될 때만 "관리" 열과 삭제 버튼이 렌더링되도록 구현했습니다.
- **삭제 실행 전 검증 및 피드백**: 삭제 전 `window.confirm` 창으로 이름과 생년월일을 검증하도록 유도하고, "등록된 경력 사항은 함께 삭제되지 않는다"는 안내 문구를 표시하도록 했습니다.
- **비활성화 및 동기화 처리**: 삭제 처리 진행 중에는 해당 행의 삭제 버튼을 비활성화하고, 성공 시 목록 및 선택 상태를 갱신하며 실패 시 테이블 하단에 `FlowError`를 노출하도록 처리했습니다.
- **테스트 코드 추가**: `packages/utils` 내 `deleteHuman` 동작 검증을 위한 테스트 케이스 2건을 새로 작성했습니다.

## 의도
잘못 등록한 대상자를 삭제할 방법이 없어 오타가 있는 상태로 조회 목록에 유지되던 데이터 오염 문제를 해결하기 위함입니다. 또한 백엔드 데이터베이스 상에 `cascade` 옵션이 없어 대상자를 삭제하더라도 관련 경력 정보(`certificate` 행)가 고아 데이터로 남는 한계점을 UI 안내 문구로 우회 보완하여 사용자의 혼선을 최소화하고자 했습니다.

## 생각 정리
1. 데이터베이스에서 Cascade 삭제를 지원하지 않아 경력 사항이 고아 데이터로 남는 백엔드의 비즈니스 제약 사양을 해결하기 위해, 이후 스프린트에서 백엔드 개발자에게 어떤 방식의 스키마 및 외래키 옵션 수정을 건의하는 것이 가장 효율적일까요?
2. 현재 삭제 확인을 위해 브라우저 기본 UI인 `window.confirm`을 사용하고 있는데, 전반적인 서비스 UX 통일성을 고려했을 때 커스텀 모달 컴포넌트로 이를 교체한다면 공통 UI 라이브러리를 어떻게 개선해야 할까요?
3. 이번 백엔드 API 연동 작업을 진행하며, 프론트엔드가 백엔드 스키마 제약 사항을 극복하기 위해 사용자 안내 문구나 UI 잠금 처리 등을 정교하게 보완하는 과정에서 개발자로서 어떤 세심함을 배울 수 있었나요?
